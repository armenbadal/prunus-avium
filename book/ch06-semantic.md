# Իմաստային վերլուծություն

Շարահյուսական վերլուծության արդյունքում Կեռաս ծրագրից կառուցվում է վերացական
շարահյուսական ծառ։ Այդ ծառը, բնականաբար, արտացոլում է տրված ծրագրի
շարահյուսությունը։ Բայց շարահյուսորեն ճիշտ ամեն մի ծրագիր դեռ պարտադիր չէ, որ
իմաստ ունենա։ Դիտարկենք մի պարզ օրինակ.

```basic
SUB Main
    DIM r AS REAL
    DIM t AS TEXT
    DIM b AS BOOL
    LET b = r * t
END SUB
```

Սա շարահյուսորեն ճիշտ ծրագիր է։ `DIM` հրամաններով հայտարարված են երեք
փոփոխականներ, իսկ `LET` հրամանով `b` փոփոխականին վերագրվում է `r * t`
արտահայտության արժեքը։ Շարահյուսական վերլուծիչը կարող է վստահորեն կառուցել
այս ծրագրի ծառը։ Այնուամենայնիվ ծրագրում երկու սխալ կա։ Նախ՝ `REAL` տիպի
`r` արժեքը հնարավոր չէ բազմապատկել `TEXT` տիպի `t` արժեքով։ Ապա՝ `BOOL`
տիպի `b` փոփոխականին հնարավոր չէ վերագրել թվաբանական գործողության `REAL`
արդյունքը։

Նման սխալները հնարավոր չէ գտնել միայն քերականական կանոններով։ Դրանք
հայտնաբերելու համար պետք է իմանալ, թե ամեն մի անուն որտեղ է հայտարարված, ինչ
դեր ունի, ինչ տիպի արժեք է ներկայացնում և տվյալ գործողությունն ինչ տիպի
արգումենտներ է պահանջում։ Հենց այս աշխատանքն է կատարում _իմաստային
վերլուծիչը_։

Կեռասի կոմպիլյատորում իմաստային վերլուծությունը կատարվում է շարահյուսական
վերլուծությունից հետո և կոդի գեներացիայից առաջ։ Այս փուլի մուտքը `Program`
հանգույցով ներկայացված շարահյուսական ծառն է։ Արդյունքում ստանում ենք.

* `SemanticModel` օբյեկտ, որում գրանցված են անունների ու տիպերի մասին
  տեղեկությունները,
* `Diagnostics` օբյեկտ, որում կուտակված են հայտնաբերված սխալները։

Իմաստային վերլուծիչը չի փոխում շարահյուսական ծառը։ Ծառն առաջվա պես նկարագրում
է ծրագրի կառուցվածքը, իսկ վերլուծության ընթացքում պարզված լրացուցիչ
տեղեկությունները պահվում են առանձին մոդելում։ Այս բաժանումը թույլ է տալիս նույն
ծառը հետագայում օգտագործել կոմպիլյատորի տարբեր փուլերում՝ առանց այն նորանոր
դաշտերով ծանրաբեռնելու։


## Սիմվոլներ

Անունների իմաստը ներկայացնելու համար օգտագործվում են _սիմվոլներ_։ Ծրագրում
հանդիպող `count` անունը կարող է լինել լոկալ փոփոխական, ենթածրագրի պարամետր կամ
`FOR` հրամանի հաշվիչ։ Միայն անունը բավարար չէ հասկանալու համար, թե դրանցից
որն է նկատի առնված։ Սիմվոլն անունին կցում է կոմպիլյատորին անհրաժեշտ այդ
տեղեկությունները։

Սիմվոլների հետ կապված տիպերը սահմանված են `symbols.hxx` ֆայլում։ Բոլոր
սիմվոլների ընդհանուր մասը `Symbol` ստրուկտուրան է.

```cpp
struct Symbol {
    explicit Symbol(std::string name);

    SymbolId id{UnknownSymbol};
    std::string name;
};
```

Ամեն մի հաջողությամբ հայտարարված սիմվոլ ստանում է իր եզակի `SymbolId`
արժեքը։ `UnknownSymbol` զրոյական արժեքը պահուստային նշիչ է. այն վերադարձվում
է, օրինակ, երբ նույն տեսանելիության տիրույթում արդեն գոյություն ունեցող անունը
նորից հայտարարելու փորձ է արվում։

Կեռասի անունները բաժանվում են երկու հիմնական խմբի՝ փոփոխականներ և
ենթածրագրեր։ Դրանք ներկայացված են `VariableSymbol` ու `SubroutineSymbol`
ստրուկտուրաներով.

```cpp
struct VariableSymbol final : Symbol {
    const Type* type;
    VariableStorage storage{VariableStorage::Local};
};

struct SubroutineSymbol final : Symbol {
    SubroutineSignature signature;
    bool builtin{false};
};
```

Փոփոխականի սիմվոլում պահվում է նրա տիպը։ `storage` դաշտը ցույց է տալիս, թե
փոփոխականն ինչպես է առաջացել։ Այն կարող է լինել `DIM` հրամանով հայտարարված
լոկալ փոփոխական, ենթածրագրի պարամետր կամ `FOR` հրամանի համար անբացահայտ
կերպով ստեղծված հաշվիչ։

Ենթածրագրի սիմվոլում պահվում են նրա _ստորագրությունն_ ու `builtin` հայտանիշը։
Ստորագրությունը բաղկացած է պարամետրերի տիպերի ցուցակից և վերադարձվող տիպից.

```cpp
struct SubroutineSignature {
    std::vector<const Type*> parameters;
    const ScalarType* returnType{};
};
```

Եթե `returnType`-ը `nullptr` է, ապա ենթածրագիրը պրոցեդուրա է և արժեք չի
վերադարձնում։ Մյուս դեպքում գործ ունենք ֆունկցիայի հետ։ Պարամետրերի ցուցակում
`ScalarType` օբյեկտի ցուցիչը նշանակում է պարզ պարամետր, իսկ `ArrayType`
օբյեկտի ցուցիչը՝ զանգվածային պարամետր։ Ներդրված ենթածրագրերի համար այստեղ
կիրառվում է նաև `nullptr` արժեքը. դրանով նշվում է ցանկացած տիպի պարզ
պարամետր։ Այդ հնարավորությանը դեռ կվերադառնանք։

Փոփոխականի ու ենթածրագրի սիմվոլները `SymbolTable`-ում պահվում են միևնույն
ցուցակում։ Դրա համար օգտագործված է `std::variant` տիպը.

```cpp
using SymbolValue = std::variant<VariableSymbol, SubroutineSymbol>;
```

Այսպիսի ներկայացմամբ ամեն սիմվոլ պարունակում է միայն իր տեսակի համար
իմաստալից դաշտերը։ `symbol()` մեթոդը վերադարձնում է դրանց ընդհանուր մասը, իսկ
`variable()` և `subroutine()` մեթոդները՝ համապատասխան կոնկրետ տիպի ցուցիչը։
Եթե, օրինակ, փոփոխականի `SymbolId`-ն փոխանցված է `subroutine()` մեթոդին, ապա
արդյունքը `nullptr` է։


## Սիմվոլների աղյուսակը

Սիմվոլ ստեղծելը դեռ գործի կեսն է։ Պետք է նաև կարողանալ ծրագրի որևէ կետում
օգտագործված անունով գտնել հենց այն սիմվոլը, որի հայտարարումը տեսանելի է այդ
կետից։ Այս գործը կատարում է `SymbolTable` դասը։

Սիմվոլների աղյուսակում անունների տեսանելիության տիրույթները պահվում են ստեկի
տեսքով.

```cpp
using Scope = std::unordered_map<std::string, SymbolId>;

std::vector<SymbolValue> _symbols;
std::vector<Scope> _scopes;
SymbolId _nextId{1};
```

Ամեն մի `Scope` անունը համապատասխանեցնում է սիմվոլի համարին։ Իսկ բուն
սիմվոլները պահվում են `_symbols` ցուցակում։ Այս բաժանումն ունի մի կարևոր
առավելություն. նույն սիմվոլին կարելի է հղվել կայուն համարով՝ անկախ նրանից, թե
որ տեսանելիության տիրույթից է այն գտնվել կամ քանի նոր անուն է ավելացվել
աղյուսակում։

`SymbolTable` օբյեկտի կառուցման պահին բացվում է առաջին՝ գլոբալ տիրույթը։ Նոր
տիրույթ բացելու և փակելու համար սահմանված են `openScope()` ու `closeScope()`
մեթոդները։ Փոփոխականը միշտ ավելացվում է ստեկի գագաթում գտնվող ընթացիկ
տիրույթում, իսկ ենթածրագիրը՝ գլոբալ տիրույթում։

Անունը որոնող `lookup()` մեթոդը տիրույթներն անցնում է հակառակ հերթականությամբ՝
ամենաներսինից դեպի գլոբալը։ Ուրեմն, եթե ներսի տիրույթում հայտարարված անունը
նույնն է, ինչ դրսի տիրույթում եղածինը, ապա կգտնվի ներսինը։ Սա անունների
_ծածկման_ սովորական կանոնն է։

Ենթածրագրերի համար սահմանված է առանձին `lookupSubroutine()` մեթոդ։ Ինչո՞ւ չի
բավականացնում սովորական որոնումը։ Դիտարկենք այսպիսի ֆունկցիա.

```basic
SUB Sum(Sum AS REAL, value AS REAL) AS REAL
    IF Sum = 0 THEN
        RETURN value
    ELSE
        RETURN Sum(Sum - 1, value + Sum)
    END IF
END SUB
```

Այստեղ պայմանի ու գումարման մեջ հանդիպող `Sum` անունը պարամետր է և ծածկում է
գլոբալ `Sum` ֆունկցիայի անունը։ Սակայն `Sum(Sum - 1, value + Sum)` գրառման
առաջին `Sum`-ը պետք է որոնվի որպես ենթածրագիր։ `lookupSubroutine()`-ը, լոկալ
փոփոխական գտնելով, չի կանգնում և շարունակում է որոնումը մինչև գլոբալ
ենթածրագիրը։

Կեռասում `IF`, `WHILE` և `FOR` կառուցվածքների մարմինները նոր տեսանելիության
տիրույթ չեն ստեղծում։ Յուրաքանչյուր ենթածրագրի ամբողջ մարմինն ունի մեկ լոկալ
տիրույթ։ Հետևաբար, որևէ ճյուղի կամ ցիկլի ներսում հայտարարված անունը տեսանելի է
նույն ենթածրագրի ամբողջ մարմնում և չի կարող մեկ այլ ճյուղում նորից
հայտարարվել։ Այս կանոնն ավելի մանրամասն կքննարկենք անունների որոշման անցման
ժամանակ։


## Իմաստային մոդելը

Դիտարկենք հետևյալ երկու հրամանները.

```basic
DIM radius AS REAL
LET radius = 12.5
```

Ծառում `DIM` հայտարարումն ու `LET` հրամանի ձախ կողմի `radius` փոփոխականը
տարբեր հանգույցներ են։ Դրանք ունեն տարբեր `NodeId` արժեքներ, բայց երկուսն էլ
վերաբերում են նույն սիմվոլին։ Իմաստային վերլուծիչը պետք է պահի հենց այդ կապը։

Մյուս կողմից, կոդ գեներացնելիս անհրաժեշտ է իմանալ ոչ միայն անունների դերերը,
այլև ամեն մի արտահայտության տիպը։ Օրինակ, `radius * 2` արտահայտության ծառի
գագաթին բինար գործողություն է, որի արդյունքի `REAL` տիպը բացահայտ գրված չէ
ծառի մեջ։ Այն հաշվարկվում է իմաստային վերլուծության ժամանակ։

Այս երկու տեսակի տեղեկությունները հավաքվում են `SemanticModel` դասում.

```cpp
class SemanticModel {
public:
    void bind(NodeId node, SymbolId symbol);
    void setEntryPoint(SymbolId symbol);
    void setType(NodeId node, const Type& type);

    std::optional<SymbolId> symbol(NodeId node) const;
    std::optional<SymbolId> entryPoint() const;
    const Type* type(NodeId node) const;

private:
    std::unordered_map<NodeId, SymbolId> _symbols;
    std::optional<SymbolId> _entryPoint;
    std::unordered_map<NodeId, const Type*> _types;
};
```

Առաջին աղյուսակը AST հանգույցը կապում է սիմվոլին։ Երկրորդը պահում է ծրագրի
մուտքի կետը՝ `Main` ենթածրագրի սիմվոլը։ Երրորդ աղյուսակը յուրաքանչյուր
հաշվարկված արտահայտության հանգույցը կապում է իր տիպին։

Նկատենք, որ `SemanticModel`-ը պահում է տիպերի ցուցիչները, բայց չի տնօրինում
այդ օբյեկտները։ Փոփոխականների ու ենթածրագրերի տիպերը պատկանում են
շարահյուսական ծառին, իսկ լիտերալների ու գործողությունների ընդհանուր `BOOL`,
`REAL` և `TEXT` տիպերն ապրում են ամբողջ ծրագրի աշխատանքի ընթացքում։ Հետևաբար
դրանք հասանելի են այնքան ժամանակ, որքան անհրաժեշտ է իմաստային մոդելն
օգտագործող հաջորդ փուլերին։


## Վերլուծության երկու անցումները

Թվում է, թե կարելի է ծառը մեկ անգամ վերևից ներքև անցնել, հանդիպած անունները
գրանցել և տեղում ստուգել տիպերը։ Բայց այդ պարզ սխեման բավարար չէ։ Կեռասում
ենթածրագիրը կարելի է կանչել իր հայտարարումից առաջ.

```basic
SUB Main
    CALL Show
END SUB

SUB Show
    CALL Print "Ok"
END SUB
```

Նույնպիսի հարց է առաջանում նաև լոկալ անունների դեպքում։ Քանի որ `IF`-ի ու
ցիկլերի մարմիններն առանձին տիրույթներ չեն ստեղծում, ներսում հայտարարված անունը
պետք է ճանաչելի լինի ամբողջ ենթածրագրում՝ նույնիսկ հայտարարումից առաջ։

Այս պատճառով Կեռասի իմաստային վերլուծիչն աշխատում է երկու հիմնական անցումով.

```text
Program AST
    |
    +-- NameResolutionPass --> SymbolTable + անունների կապեր + Diagnostics
    |
    +-- TypeCheckingPass   --> արտահայտությունների տիպեր + Diagnostics
```

Առաջին անցումով՝ `NameResolutionPass`-ով, որոշվում են անունների դերերը և
կառուցվում է սիմվոլների աղյուսակը։ Երկրորդով՝ `TypeCheckingPass`-ով,
հաշվարկվում են արտահայտությունների տիպերն ու ստուգվում լեզվի տիպային կանոնները։
Երկու անցումներն էլ կարող են ախտորոշումներ ավելացնել ընդհանուր `Diagnostics`
օբյեկտում։

Այս դասերը սահմանված են `semantic.cxx` ֆայլի անանուն անունների տիրույթում։
Դրանք իրականացման ներքին մանրամասներ են և կոմպիլյատորի մնացած մասերին
տեսանելի չեն։ Արտաքին ինտերֆեյսը միայն `SemanticAnalyzer` դասն է։


## Անունների դերերի որոշումը

`NameResolutionPass`-ը `ASTVisitor`-ից ածանցված դաս է։ Այն անցնում է ծառի
հանգույցներով, հայտարարումների համար նոր սիմվոլներ է ստեղծում, իսկ անունների
օգտագործումները կապում է արդեն ստեղծված սիմվոլներին։ Ծրագրի մակարդակում
աշխատանքի հերթականությունը հետևյալն է.

```cpp
void NameResolutionPass::visit(Program& program)
{
    declareBuiltins();
    declareSubroutines(program);
    resolveEntryPoint(program);

    for( const auto& subroutine : program._subroutines )
        visit(*subroutine);
}
```

Այս մի քանի տողերում կարևոր է հենց գործողությունների հերթականությունը։ Նախ
գրանցվում են ներդրված ենթածրագրերը, հետո՝ ծրագրավորողի հայտարարած բոլոր
ենթածրագրերը։ Միայն դրանից հետո են վերլուծվում դրանց մարմինները։ Ահա թե ինչու
վերը բերված `Main` ենթածրագիրը կարող էր կանչել իրենից հետո գրված `Show`
պրոցեդուրան։ Նույն պատճառով առանց հատուկ բացառության աշխատում են նաև
ռեկուրսիվ կանչերը։


### Ենթածրագրերի հայտարարումները և `Main`-ը

Ենթածրագիրը գրանցելիս նրա պարամետրերի տիպերից ու վերադարձվող տիպից կառուցվում
է `SubroutineSignature` օբյեկտ։ Այնուհետև նոր `SubroutineSymbol`-ը ավելացվում
է գլոբալ տիրույթում, իսկ հայտարարող AST հանգույցը `SemanticModel::bind()`
մեթոդով կապվում է ստեղծված սիմվոլին։ Հետագայում բոլոր կանչերն էլ կկապվեն հենց
նույն `SymbolId` արժեքին։

Ենթածրագրերի անունները պետք է լինեն եզակի։ Եթե անունն արդեն պատկանում է
ծրագրավորողի հայտարարած ենթածրագրի, ապա գրանցվում է կրկնակի հայտարարում։ Եթե
այն ներդրված ենթածրագրի անուն է, տրվում է ավելի հստակ հաղորդագրություն։ Այսպես
չի կարելի, օրինակ, նորից սահմանել `Print` կամ `SQR` անունները։

Ապա `resolveEntryPoint()` մեթոդը որոնում է ծրագրի մուտքի կետը։ Կեռասի ամեն մի
կատարվող ծրագիր պետք է ունենա ճիշտ մեկ `Main` ենթածրագիր։ Այն պետք է լինի
պրոցեդուրա և պարամետրեր չունենա։ Այսինքն՝ ընդունելի է միայն հետևյալ ընդհանուր
ձևը.

```basic
SUB Main
    ' ծրագրի հրամանները
END SUB
```

Եթե `Main`-ը բացակայում է, սխալը կապվում է ամբողջ `Program` հանգույցին։ Եթե
ունի պարամետր կամ վերադարձվող տիպ, սխալը կապվում է հենց նրա հայտարարությանը։
Հաջող ստուգման դեպքում `Main`-ի սիմվոլը գրանցվում է `SemanticModel`-ում որպես
մուտքի կետ։


### Պարամետրերը և լոկալ հայտարարումները

Ենթածրագրի մարմինը վերլուծելուց առաջ բացվում է նոր տիրույթ։ Նախ այդ տիրույթում
գրանցվում են պարամետրերը, ապա՝ մարմնի բոլոր լոկալ հայտարարումները։ Միայն
դրանից հետո է սկսվում անունների օգտագործումները լուծող անցումը։

```cpp
void NameResolutionPass::visit(Subroutine& subroutine)
{
    _symbols.openScope();
    declareParameters(subroutine);
    declareLocals(*subroutine._body);
    visit(*subroutine._body);
    _symbols.closeScope();
}
```

`declareLocals()` մեթոդը ռեկուրսիվ անցնում է `IF`, `WHILE` ու `FOR`
կառուցվածքների մարմիններով և հավաքում այնտեղ հանդիպող `DIM` հայտարարումները։
Այս նախնական հավաքումն իրականացնում է վերը նկարագրված կանոնը՝ մեկ ենթածրագրի
ամբողջ մարմինը դիտարկել որպես մեկ տեսանելիության տիրույթ։

Օրինակ, հետևյալ ծրագրում `value` անունը ճանաչելի է նաև հայտարարումից առաջ.

```basic
SUB Main
    LET value = 7
    IF TRUE THEN
        DIM value AS REAL
    END IF
END SUB
```

Թեև գրառման այս ոճը դժվար թե խորհուրդ տանք, այն համապատասխանում է Կեռասի
տեսանելիության կանոնին։ Մյուս կողմից, նույն անունը երկրորդ անգամ չի կարելի
հայտարարել մեկ այլ ճյուղում կամ ցիկլում։ Պարամետրերը, `DIM` հայտարարումներն ու
`FOR`-ի հաշվիչները միասին են մասնակցում եզակիության ստուգմանը։

Հայտարարումների հավաքման ժամանակ արտահայտությունները դեռ չեն ստուգվում։
Օրինակ, `DIM values[count] AS REAL` հայտարարության `count` անունը լուծվում է
առաջին անցման ժամանակ, բայց չափի արտահայտության տիպն ու հնարավոր հաստատուն
արժեքը ստուգվում են երկրորդ անցումով։ Այս բաժանումը թույլ է տալիս ամեն մի
անցմանը զբաղվել իր հստակ գործով։


### `FOR` հրամանի հաշվիչը

`FOR`-ի հաշվիչն առանձնահատուկ անուն է, որովհետև այն կարելի է նախապես
չհայտարարել.

```basic
FOR index = 0 TO 10
    CALL Print index
END FOR
```

Եթե ընթացիկ տիրույթում `index` անունով փոփոխական չկա, ապա իմաստային
վերլուծիչն ինքն է ստեղծում `REAL` տիպի և `ForVariable` պահպանման դերով
սիմվոլ։ Այդ անունը տեսանելի է դառնում ամբողջ ենթածրագրում։

Եթե նույն անունով փոփոխական արդեն հայտարարված է, նորը չի ստեղծվում, այլ
օգտագործվում է գոյություն ունեցողը։ Սակայն այն պարտադիր պետք է լինի պարզ
`REAL` փոփոխական։ `TEXT`, `BOOL` կամ զանգվածային փոփոխականը չի կարող ծառայել
որպես `FOR`-ի հաշվիչ։


### Անունների օգտագործումները

Ծառում `Variable` հանգույց հանդիպելիս `resolveVariable()` մեթոդը անունը
որոնում է սիմվոլների աղյուսակում։ Եթե այն չկա, ստանում ենք «փոփոխական
սահմանված չէ» սխալը։ Եթե անունը կա, բայց ենթածրագիր է, ապա ստանում ենք «անունը
փոփոխական չէ» սխալը։ Հաջողության դեպքում հանգույցը կապվում է փոփոխականի
սիմվոլին։

Նույն ձևով `Call` և `Apply` հանգույցների անունները մշակվում են
`resolveSubroutine()` մեթոդով։ Այստեղ որոնումը կատարվում է միայն
ենթածրագրերի մեջ։ Կանչի արգումենտների քանակն ու տիպերն այս պահին դեռ չեն
ստուգվում. առաջին անցմանը բավական է գտնել կանչվող ենթածրագիրն ու կապը գրանցել
իմաստային մոդելում։


## Տիպերի ստուգումը

Երբ երկրորդ անցումը սկսվում է, անունների մասին անհրաժեշտ տեղեկությունն արդեն
պատրաստ է։ `TypeCheckingPass`-ը նորից անցնում է ամբողջ ծառով, բայց այլևս չի
բացում տեսանելիության տիրույթներ և անուններ չի որոնում։ `Variable`, `Call` կամ
`Apply` հանգույցի սիմվոլը այն վերցնում է `SemanticModel`-ից։

Կեռասն ունի երեք պարզ տիպ՝ `BOOL`, `REAL` և `TEXT`, ինչպես նաև դրանց
միաչափ զանգվածները։ Արտահայտության տիպը ստանալու ընդհանուր կետը
`expressionType()` մեթոդն է.

```cpp
const Type* TypeCheckingPass::expressionType(Expression& expression)
{
    if( const auto type = _model.type(expression.id()) )
        return type;

    visit(expression);
    return _model.type(expression.id());
}
```

Մեթոդը նախ ստուգում է՝ արդյոք տվյալ հանգույցի տիպն արդեն հաշվարկված է։ Եթե
այո, վերադարձնում է մոդելում եղած արժեքը։ Հակառակ դեպքում այցելում է
արտահայտության հանգույցը, հաշվարկում տիպը և նորից կարդում այն մոդելից։ Այսպես
հաջողությամբ տիպավորված նույն արտահայտությունը երկրորդ անգամ ստուգելու կարիք
չի լինում։

Լիտերալների տիպերը որոշվում են անմիջապես. `Boolean`-ը `BOOL` է, `Number`-ը՝
`REAL`, իսկ `Text`-ը՝ `TEXT`։ Փոփոխականի տիպը վերցվում է առաջին անցումով
կապված `VariableSymbol`-ից։ Եթե անունը չի լուծվել, ապա տիպի փոխարեն
վերադարձվում է `nullptr`։ Դա հատուկ «անհայտ» տիպ չէ. պարզապես նշանակում է,
որ տվյալ արտահայտության մասին հավաստի տիպային տեղեկություն չունենք։

Այս մոտեցումը կարևոր է սխալների հաղորդման համար։ Եթե փոփոխականն անծանոթ է,
ապա նրա մասնակցությամբ գործողության համար երկրորդ՝ «սխալ տիպ» հաղորդագրություն
տալ պետք չէ։ Բուն պատճառի՝ անծանոթ անվան մասին սխալն արդեն գրանցված է առաջին
անցումով։


### Միտեղանի և երկտեղանի գործողությունները

Միտեղանի գործողությունների ստուգումը սկսվում է օպերանդի տիպը հաշվելով։ `NOT`
գործողության օպերանդը պետք է լինի պարզ `BOOL`, իսկ ունար `+` ու `-`
գործողություններինը՝ պարզ `REAL`։ Գործողության արդյունքի տիպը նույնպես
գրանցվում է մոդելում։

Երկտեղանի գործողությունների տիպային կանոններն ամփոփված են հետևյալ աղյուսակում.

| Գործողություններ | Օպերանդների տիպերը | Արդյունքի տիպը |
|:-----------------|:-------------------|:---------------|
| `+`, `-`, `*`, `/`, `\`, `MOD`, `^` | երկու պարզ `REAL` | `REAL` |
| `AND`, `OR` | երկու պարզ `BOOL` | `BOOL` |
| `&` | երկու պարզ `TEXT` | `TEXT` |
| `=`, `<>` | նույն տիպի երկու պարզ արժեք | `BOOL` |
| `>`, `>=`, `<`, `<=` | երկու `REAL` կամ երկու `TEXT` | `BOOL` |
| `a[i]` | զանգված և պարզ `REAL` ինդեքս | զանգվածի տարրի տիպը |

Ամբողջ զանգվածը թվաբանական, տրամաբանական կամ համեմատման գործողության օպերանդ
լինել չի կարող։ Այդ ընդհանուր ստուգումն առանձնացված է `requireScalar()`
մեթոդում։ Եթե արտահայտությունը զանգվածային է, մեթոդն ախտորոշում է սխալ և
վերադարձնում `false`։

Նկատենք նաև մեկ ուրիշ կարևոր մանրամասն։ Եթե գործողության արդյունքի տիպը
հայտնի է, այն գրանցվում է նույնիսկ օպերանդի սխալի դեպքում։ Օրինակ, սխալ
կազմված համեմատության արդյունքը, միևնույն է, `BOOL` է։ Դա թույլ է տալիս
շարունակել արտաքին արտահայտության ստուգումը և միաժամանակ խուսափել նույն
պատճառից ծնված ավելորդ սխալներից։


### Վերագրումը

`LET` հրամանը ստուգելիս նախ իմաստային մոդելից վերցվում է ձախ կողմի
փոփոխականի սիմվոլը։ Ապա հաշվարկվում են ինդեքսի և վերագրվող արտահայտության
տիպերը։ Այստեղ պետք է տարբերակել չորս դեպք.

* պարզ փոփոխականը չի կարելի ինդեքսավորել,
* ամբողջ զանգվածին չի կարելի արժեք վերագրել,
* ամբողջ զանգվածը չի կարելի օգտագործել որպես պարզ վերագրվող արժեք,
* վերագրվող արժեքի տիպը պետք է համընկնի փոփոխականի կամ զանգվածի տարրի տիպին։

Այս կանոններով, օրինակ, ընդունելի է `LET values[i] = 0`, եթե `values`-ը
`REAL` տարրերի զանգված է և `i`-ն էլ `REAL` է։ Իսկ `LET values = 0` կամ
`LET value = values` գրառումներն իմաստային սխալներ են։


### Զանգվածի չափն ու ինդեքսը

Լոկալ զանգվածի հայտարարումը պարտադիր պետք է չափ ունենա։ Չափը որոշող
արտահայտությունը պետք է լինի պարզ `REAL` արժեք։ Եթե այն հաստատուն
արտահայտություն է, ապա վերլուծիչը նաև հաշվում է դրա արժեքը և պահանջում, որ
այն լինի վերջավոր, դրական ամբողջ թիվ։

```basic
DIM first[10] AS TEXT          ' ճիշտ է
DIM second[2 + 3 * 4] AS REAL ' նույնպես ճիշտ է
DIM third[-1] AS BOOL         ' սխալ է
DIM fourth[2.5] AS REAL       ' սխալ է
```

Հաստատուն արժեքը հաշվում է `constantReal()` օժանդակ ֆունկցիան։ Այն ճանաչում
է թվային լիտերալները, ունար `+` ու `-` գործողությունները և թվաբանական
երկտեղանի գործողությունները։ Եթե ենթաարտահայտության մեջ փոփոխական կա կամ
հանդիպում է զրոյի վրա բաժանում, արդյունքը `std::nullopt` է։ Այս դեպքում
վերլուծիչը չի կարող չափի արժեքը որոշել կոմպիլյացիայի պահին և արժեքային
ստուգումը թողնում է ծրագրի կատարման փուլին։

Զանգվածի ինդեքսը նույնպես պետք է լինի պարզ `REAL`։ Ինդեքսավորման պահին
ստուգվում է նաև, որ ձախ կողմի արտահայտությունն իսկապես զանգված լինի։ Եթե այդ
երկու պայմանը կատարված են, `a[i]` արտահայտության տիպը դառնում է `a` զանգվածի
տարրի տիպը։

Սակայն ոչ բոլոր ստուգումներն է հնարավոր կատարել կոմպիլյացիայի պահին։
Դինամիկ հաշվարկված չափի դրական ու ամբողջ լինելը, ինդեքսի ամբողջ արժեք ունենալը
և զանգվածի սահմաններում գտնվելը կախված են կատարման ժամանակի արժեքներից։ Դրանք
պետք է ստուգվեն հաջորդ՝ ծրագրի կատարման փուլում։


### Ղեկավարող կառուցվածքները

`IF`-ի առաջին և բոլոր `ELSEIF` ճյուղերի պայմանները պետք է լինեն պարզ `BOOL`
արտահայտություններ։ Նույն կանոնն է կիրառվում `WHILE`-ի պայմանի համար։ `ELSE`
ճյուղը պայման չունի, ուստի պարզապես այցելվում են նրա հրամանները։

`FOR` հրամանի սկզբնական արժեքը, վերջնական արժեքն ու քայլը պետք է լինեն պարզ
`REAL` արտահայտություններ։ `Parser`-ը քայլը ներկայացնում է որպես թվային
լիտերալ, իսկ իմաստային վերլուծիչը լրացուցիչ ստուգում է, որ այն զրո չլինի։
Հաշվիչի անունն ու տիպը, ինչպես արդեն տեսանք, ստուգվել են առաջին անցումով։


### `RETURN` հրամանը

`RETURN`-ը թույլատրելի է միայն արժեք վերադարձնող ֆունկցիայում։ Վերադարձվող
արտահայտությունը պետք է լինի պարզ արժեք, իսկ նրա տիպը պետք է համընկնի
ֆունկցիայի հայտարարած վերադարձվող տիպին։ Օրինակ.

```basic
SUB Positive(value AS REAL) AS BOOL
    RETURN value > 0
END SUB
```

Բացի առանձին `RETURN` հրամանը ստուգելուց, վերլուծիչը համոզվում է, որ
ֆունկցիայի կատարման բոլոր հնարավոր ուղիներից արժեք է վերադարձվում։ Պարզ
`RETURN` հրամանն ավարտում է տվյալ ուղին։ `IF` կառուցվածքը երաշխավորված վերադարձ
է համարվում միայն այն դեպքում, երբ ունի `ELSE` ճյուղ, և իր բոլոր `IF`,
`ELSEIF` ու `ELSE` ճյուղերն էլ երաշխավորված արժեք են վերադարձնում։

```basic
SUB Sign(value AS REAL) AS TEXT
    IF value < 0 THEN
        RETURN "negative"
    ELSEIF value > 0 THEN
        RETURN "positive"
    ELSE
        RETURN "zero"
    END IF
END SUB
```

Ցիկլի մարմնի `RETURN`-ը երաշխավորված վերադարձ չի համարվում, որովհետև ցիկլը
կարող է ոչ մի անգամ չկատարվել։ Այս ստուգումը պահպանողական է, բայց հուսալի.
այն ընդունում է միայն այն դեպքերը, որոնցում վերադարձն ակնհայտ է ծառի
կառուցվածքից։


## Ենթածրագրերի կանչերը

Կեռասում ենթածրագիրը կարելի է կանչել երկու ձևով։ `CALL Name ...` հրամանը
նախատեսված է պրոցեդուրաների համար, իսկ `Name(...)` արտահայտությունը՝ արժեք
վերադարձնող ֆունկցիաների համար։ Առաջին անցումը երկու դեպքում էլ միայն գտնում
է ենթածրագրի սիմվոլը։ Երկրորդ անցումն արդեն ստուգում է կանչի ձևն ու
արգումենտները։

`validateArguments()` մեթոդը նախ համեմատում է պարամետրերի և արգումենտների
քանակները։ Եթե դրանք տարբեր են, սխալ է գրանցվում, բայց ստուգումը դրանով չի
ավարտվում։ Առկա զույգերի համար շարունակվում են տիպերի ստուգումները, որպեսզի
մեկ կանչում եղած մի քանի անկախ սխալներից հնարավորին չափ շատերը հայտնաբերվեն։

Ամեն մի արգումենտի համար ստուգվում է երկու բան՝ նրա _ձևը_ և _բազային տիպը_։
Զանգվածային պարամետրին կարելի է փոխանցել միայն ամբողջ զանգված, իսկ պարզ
պարամետրին՝ միայն պարզ արժեք։ Դրանից հետո համեմատվում են `BOOL`, `REAL` կամ
`TEXT` բազային տիպերը։ Ֆունկցիայի հաջող կիրառման դեպքում `Apply` հանգույցի
տիպը դառնում է ստորագրության վերադարձվող տիպը։

Նույն մեխանիզմն օգտագործվում է նաև Կեռասի ներդրված ենթածրագրերի համար։ Դրանց
ստորագրությունները հավաքված են մեկ ցուցակում.

```cpp
static const std::vector<SubroutineSymbol> subroutines{
    {"Print", {{nullptr}, nullptr}, true},
    {"Input", {{}, &text}, true},
    {"NUM", {{&text}, &real}, true},
    {"SQR", {{&real}, &real}, true},
};
```

Այս գրառումները կարդանք հերթով։ `Print`-ը ցանկացած տիպի մեկ պարզ արժեք
ընդունող պրոցեդուրա է։ `Input`-ը պարամետր չունեցող ու `TEXT` վերադարձնող
ֆունկցիա է։ `NUM`-ը `TEXT` է ընդունում և `REAL` վերադարձնում։ Վերջապես,
`SQR`-ը `REAL` է ընդունում և `REAL` վերադարձնում։

Այս ներկայացումը տվյալահեն է. `validateArguments()` մեթոդում չկա `NUM`-ի կամ
`SQR`-ի անունը ստուգող հատուկ ճյուղ։ Նոր ներդրված ենթածրագիր ավելացնելու
համար բավական է նկարագրել ևս մեկ ստորագրություն։ Օրինակ, եթե ունենանք
`IsEmpty(TEXT) AS BOOL` ֆունկցիա, ապա ցուցակում կարող ենք ավելացնել.

```cpp
const auto& boolean = scalarType(ScalarType::Name::Bool);
{"IsEmpty", {{&text}, &boolean}, true},
```

Արգումենտների քանակի, ձևի ու տիպի, ինչպես նաև պրոցեդուրա կամ ֆունկցիա լինելու
բոլոր ստուգումները նոր ստորագրության համար կաշխատեն առանց այլ փոփոխության։


## Սխալների կուտակումը

Ինչպես շարահյուսական վերլուծիչը, իմաստային վերլուծիչն էլ առաջին սխալի վրա չի
կանգնում։ Երկու անցումների `report()` մեթոդները հաղորդագրությունն ու հանգույցի
տողի համարը փոխանցում են ընդհանուր `Diagnostics` օբյեկտին, ապա ծառի անցումը
շարունակվում է այնքանով, որքանով առկա տվյալները վստահելի են։

Օրինակ, եթե կանչվող ենթածրագիրը չի գտնվել, ապա նրա ստորագրությունն այլևս
հնարավոր չէ ստուգել։ Սակայն կանչի բոլոր արգումենտները միևնույն է այցելվում են,
և դրանց մեջ եղած՝ այդ սխալից անկախ խնդիրները չեն կորչում։ Նույն ձևով չլուծված
փոփոխականի տիպային ստուգումը բաց է թողնվում, քանի որ նրա տիպի մասին վստահելի
տեղեկություն չկա։

`Diagnostics`-ը հաշվում է բոլոր սխալները, բայց հիշողության մեջ պահում է
առավելագույնը առաջին ութը՝ `MaxErrors` սահմանին համապատասխան։ Եթե սխալներն
ավելի շատ են, հրամանային տողի ծրագիրը պահված հաղորդագրություններից հետո նշում
է նաև բաց թողնվածների քանակը։ Այս սահմանը թույլ չի տալիս, որ անհաջող
վերլուծությունը լցնի հիշողությունը իրար հաջորդող հազարավոր հաղորդագրություններով։

`SemanticAnalyzer::analyze()` մեթոդը հերթով գործարկում է երկու անցումները և
վերադարձնում է `true`, եթե ոչ մի ախտորոշում չի գրանցվել.

```cpp
bool SemanticAnalyzer::analyze(Program& program)
{
    NameResolutionPass nameResolution{_symbols, _model, _diagnostics};
    nameResolution.visit(program);

    TypeCheckingPass typeChecking{_symbols, _model, _diagnostics};
    typeChecking.visit(program);

    return _diagnostics.count() == 0;
}
```

Նույնիսկ անհաջող վերլուծությունից հետո `SemanticModel`-ում մնում են բոլոր
հաջողությամբ որոշված կապերն ու տիպերը։ Դրանք կարող են օգտակար լինել ոչ միայն
հաջորդ փորձի ախտորոշումները կատարելագործելու, այլ նաև ապագայում խմբագրիչի
օժանդակ գործիքներ կառուցելու համար։ Բայց նպատակային կոդի գեներացիան պետք է
սկսել միայն այն դեպքում, երբ `analyze()`-ը հաջողություն է վերադարձրել։


## Թեստերը

Սիմվոլների աղյուսակի թեստերը գրված են `tests/symbols_test.cxx`, իսկ իմաստային
վերլուծիչի թեստերը՝ `tests/semantic_test.cxx` ֆայլերում։ Դրանք ստուգում են ոչ
միայն հաջող կամ անհաջող վերլուծությունը, այլ նաև կառուցված մոդելի
բովանդակությունը՝ հանգույցների կապերը, արտահայտությունների տիպերն ու ընտրված
մուտքի կետը։

Առանձին թեստերով ծածկված են `Main` ենթածրագրի կանոնները, կրկնակի
հայտարարումները, անունների տեսանելիությունը, `FOR`-ի հաշվիչը, վերագրումները,
բոլոր գործողությունների տիպերը, ղեկավարող կառուցվածքները, զանգվածները,
`RETURN` հրամանը, սովորական ու ներդրված ենթածրագրերի կանչերը։ Ամբողջ փաթեթը
կարելի է կառուցել ու փորձարկել հետևյալ հրամաններով.

```bash
$ cmake -S . -B build
$ cmake --build build
$ ctest --test-dir build --output-on-failure
```

Իմաստային վերլուծությունից հետո շարահյուսական ծառն արդեն պարզապես ծրագրի
կառուցվածքը նկարագրող օբյեկտ չէ։ Նրա անունները կապված են կոնկրետ
հայտարարումներին, արտահայտությունների տիպերը հաշվարկված են, մուտքի կետը հայտնի
է, իսկ լեզվի կանոններին հակասող կառուցվածքների մասին ախտորոշումները՝ հավաքված։
Այս տվյալներն են այն վստահելի հիմքը, որի վրա հաջորդ գլխում կառուցելու ենք
Կեռաս ծրագրի նպատակային կոդը։
