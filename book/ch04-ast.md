# Վերացական շարահյուսական ծառ


Ծրագրավորման լեզվով գրված տեքստը նախատեսված է առաջին հերթին մարդու համար։
Ծրագրավորողը տեսնում է ծառայողական բառերը, գործողությունների նշանները,
փակագծերն ու նոր տողերը և դրանցից հասկանում ծրագրի կառուցվածքը։ Սակայն
կոմպիլյատորի հաջորդ փուլերի համար տեքստային այս ձևը հարմար չէ։ Ամեն անգամ
ստիպված կլինեինք նորից որոնել բլոկների սահմանները, որոշել գործողությունների
նախապատվությունը և իրար կապել նույն կառուցվածքի մասերը։

Դիտարկենք մի փոքր Կեռաս ծրագիր.

```basic
SUB Square(value AS REAL) AS REAL
    RETURN value^2
END SUB

SUB Main
    CALL Print Square(5)
END SUB
```

Այստեղ երկու ենթածրագիր կա։ `Square`-ի մարմնում `RETURN` հրաման է, որի արժեքը
աստիճան բարձրացնելու արտահայտություն է։ `Main`-ի մարմնում `Print`
պրոցեդուրայի կանչ է, իսկ դրա միակ արգումենտը `Square` ֆունկցիայի կիրառությունն
է։ Մարդու համար այս կապերը տեսանելի են գրառման ձևից։ Կոմպիլյատորի համար դրանք
պետք է ներկայացնել բացահայտ տվյալների կառուցվածքներով։

Այդ միջանկյալ ներկայացումը _վերացական շարահյուսական ծառն_ է՝ AST-ն
(abstract syntax tree)։ Այն ծառ է, որովհետև լեզվական կառուցվածքները կազմված
են ավելի փոքր կառուցվածքներից։ Ծրագիրը պարունակում է ենթածրագրեր,
ենթածրագիրն ունի հրամանների մարմին, հրամանը կարող է պարունակել արտահայտություն,
իսկ արտահայտությունն իր հերթին՝ այլ արտահայտություններ։

Վերը բերված `value^2` արտահայտության ծառը կարելի է պատկերել այսպես.

```text
        Binary(^)
        /       \
 Variable(value) Number(2)
```

`Binary` հանգույցը գործողությունն է, իսկ նրա երկու զավակները՝ ձախ ու աջ
օպերանդները։ Նույն սկզբունքով `Square(5)` կիրառության հանգույցը պահում է
կանչվող անունն ու արգումենտի `Number` հանգույցը։

Ծառն անվանում ենք _վերացական_, որովհետև այնտեղ չեն պահպանվում սկզբնական
գրառման բոլոր մանրամասները։ Օրինակ, `RETURN` բառը, `^` նշանը և ֆունկցիայի
կլոր փակագծերը առանձին հանգույցներ չեն դառնում։ Դրանց փոխարեն կառուցվում են
`Return`, `Binary` և `Apply` օբյեկտներ, որոնք անմիջապես արտահայտում են այդ
գրառումների դերը։ Բացատների ու մեկնաբանությունների նման տարրերը ծառին
ընդհանրապես չեն հասնում։

Այս գլխում հերթով կկառուցենք Կեռասի AST հանգույցները, կտեսնենք դրանց
սեփականության կառուցվածքը և կսահմանենք ծառով անցնելու ընդհանուր մեխանիզմը։
Բոլոր հիմնական տիպերը գրված են `ast.hxx` ֆայլում և գտնվում են `avium`
անունների տիրույթում։


## Ծառի ընդհանուր կառուցվածքը

Կեռասի ծառի բոլոր հանգույցներն ուղղակիորեն կամ միջնորդավորված ածանցված են
`Node` դասից։ Դրանք կարելի է խմբավորել հետևյալ կերպ.

```text
Node
├── Expression
│   ├── Boolean, Number, Text, Variable
│   ├── Unary, Binary
│   └── Apply
├── Statement
│   ├── Dim, Let
│   ├── If, While, For
│   ├── Call
│   └── Return
├── Type
│   ├── ScalarType
│   └── ArrayType
├── Sequence
├── IfBranch
├── Subroutine
└── Program
```

`Expression`-ն արտահայտությունների ընդհանուր հիմքն է, `Statement`-ը՝
հրամաններինը, իսկ `Type`-ը՝ տիպերինը։ `Sequence`, `IfBranch`,
`Subroutine` ու `Program` հանգույցները կառուցվածքային դեր ունեն և
անմիջապես ածանցված են `Node`-ից։

Նկատենք, որ C++ դասերի այս ժառանգման ծառը նույնը չէ, ինչ Կեռաս ծրագրից
կառուցվող օբյեկտների ծառը։ Առաջինը ցույց է տալիս հանգույցների _տիպերի_
հարաբերությունները։ Երկրորդը կազմվում է կոնկրետ ծրագրի համար և ցույց է տալիս,
թե որ հանգույցն ինչ զավակներ ունի։


## Հանգույցների ընդհանուր հիմքը

`Node` դասը պահում է այն տվյալները, որոնք ընդհանուր են ծառի բոլոր
հանգույցների համար.

```cpp
using Position = std::uint32_t;
using NodeId = std::uint64_t;

class Node {
public:
    Node() = default;

    Node(NodeKind kind, Position line)
        : kind{kind}
        , line{line}
        , _id{_nextId++}
    {
    }

    virtual ~Node() = default;

    NodeId id() const noexcept
    {
        return _id;
    }

    const NodeKind kind{NodeKind::Empty};
    const Position line{0};

private:
    NodeId _id{0};
    inline static NodeId _nextId{1};
};
```

Ամեն հանգույց ունի իր տեսակը որոշող `kind`, ծրագրի տողի `line` համարը և եզակի
`NodeId`։ `kind` դաշտի հնարավոր արժեքները հավաքված են `NodeKind` թվարկման մեջ։
Այն պարունակում է ծառի բոլոր տիպերը՝ `Number`-ից ու `Binary`-ից մինչև
`Subroutine` և `Program`։

Ինչո՞ւ է հանգույցին պետք և՛ C++-ի իրական տիպը, և՛ առանձին `NodeKind` արժեքը։
Իրական տիպն անհրաժեշտ է տվյալ հանգույցի հատուկ դաշտերին դիմելու համար, իսկ
`kind`-ը թույլ է տալիս ընդհանուր `Node&` հղումից արագ որոշել այդ տիպն ու
հանգույցը փոխանցել համապատասխան մշակող մեթոդին։ Հենց այդպես է աշխատում
հետագայում քննարկվող `ASTVisitor`-ը։

`line` դաշտը պահում է միայն տողի համարը։ Օրինակ, `Let` հանգույցը ստանում է
`LET` բառի տողը, իսկ `Binary`-ն՝ գործողության նշանի տողը։ Այս տեղեկությունը
հետագա փուլերին թույլ է տալիս սխալի հաղորդագրությունը կապել ծրագրի ճիշտ
տեղին։

`NodeId`-ն ծառի հանգույցի եզակի համարն է։ Սովորական հանգույցներն այն ստանում
են `_nextId` հաշվիչից, իսկ լռելությամբ կառուցված դատարկ `Node` օբյեկտի համարը
զրո է։ Իմաստային վերլուծության ժամանակ հենց այս համարով են առանձին աղյուսակում
պահվում տվյալ հանգույցի սիմվոլն ու հաշվարկված տիպը։ Այսպիսով AST-ը չի
ծանրաբեռնվում հետագա փուլերի դաշտերով։

`Node`-ն ունի վիրտուալ դեստրուկտոր, որովհետև դրա ածանցյալ օբյեկտները հաճախ
տնօրինվում են բազային դասի ցուցիչով։ Օրինակ, `Expression::Ptr`-ը կարող է
իրականում ցույց տալ `Number`, `Binary` կամ `Apply` հանգույց։


## Հանգույցների ստեղծումն ու սեփականությունը

AST հանգույցները ստեղծելու համար սահմանված է փոքր `node<T>()` օժանդակ
կաղապարը.

```cpp
template<typename T, typename... Args>
std::unique_ptr<T> node(Args&&... args)
{
    return std::make_unique<T>(std::forward<Args>(args)...);
}
```

Օրինակ, 3.14 թվային լիտերալի հանգույցը կարելի է ստեղծել այսպես.

```cpp
auto number = node<Number>(3.14, 7);
```

Երկրորդ արգումենտը ցույց է տալիս, որ լիտերալը հանդիպել է ծրագրի յոթերորդ
տողում։ `auto`-ով որոշված `number` փոփոխականի տիպը
`std::unique_ptr<Number>` է։

Ծառի սեփականության կառուցվածքը հիմնված է `std::unique_ptr`-ի վրա։ Ամեն
հանգույց տնօրինում է իր զավակներին, իսկ ծառի արմատը տնօրինում է ամբողջ ծառը։
Օրինակ, բինար գործողության երկու օպերանդները փոխանցվում են նրա կառուցիչին.

```cpp
auto sum = node<Binary>(
    Operation::Add,
    node<Number>(1.0, 1),
    node<Number>(2.0, 1),
    1);
```

`Binary` հանգույցը դառնում է երկու `Number` հանգույցների միակ սեփականատերը։
Երբ վերացվի արմատային `Program` օբյեկտը, `unique_ptr`-ների շղթան
ինքնաբերաբար կվերացնի նաև նրա բոլոր զավակներին։

Այս ընտրությունը հստակեցնում է ծառի կառուցվածքը։ Հանգույցը չի կարող միաժամանակ
երկու տարբեր ծնող ունենալ, և հարկավոր չէ ձեռքով ղեկավարել հիշողությունը։
Կառուցիչներում զավակները տեղափոխվում են `std::move()`-ով, որովհետև
`unique_ptr`-ը պատճենել չի կարելի։

Հանգույցների բովանդակությունը կառուցումից հետո հիմնականում չի փոխվում։
Դաշտերը հայտարարված են `const`, ուստի parser-ը մի անգամ կառուցում է ծառը, իսկ
հաջորդ փուլերը կարդում են այն։ Եթե իմաստային վերլուծությունը նոր տեղեկություն է
պարզում, այն գրում է ոչ թե հանգույցի մեջ, այլ առանձին `SemanticModel`-ում։


## Գործողությունների թվարկումը

Միտեղանի ու երկտեղանի գործողությունները ծառում ներկայացվում են `Operation`
թվարկման արժեքներով.

```cpp
enum class Operation : std::uint8_t {
    None,
    Add, Sub, Mul, Div, Quot, Mod, Pow,
    Eq, Ne, Gt, Ge, Lt, Le,
    And, Or, Not,
    Conc,
    Index,
};
```

Այստեղ նույն արժեքներն օգտագործվում են թե՛ միտեղանի, թե՛ երկտեղանի
գործողությունների համար։ `Add`-ը, օրինակ, կարող է ներկայացնել բինար գումարում
կամ ունար պլյուս. հանգույցի `Unary` կամ `Binary` տիպն արդեն տարբերակում է այդ
երկու դեպքերը։

Գործողությունները կարելի է խմբավորել ըստ նշանակության.

| Խումբ | `Operation` արժեքներ | Կեռասի գրառումը |
|:------|:--------------------|:----------------|
| թվաբանական | `Add`, `Sub`, `Mul`, `Div`, `Quot`, `Mod`, `Pow` | `+`, `-`, `*`, `/`, `\`, `MOD`, `^` |
| համեմատման | `Eq`, `Ne`, `Gt`, `Ge`, `Lt`, `Le` | `=`, `<>`, `>`, `>=`, `<`, `<=` |
| տրամաբանական | `And`, `Or`, `Not` | `AND`, `OR`, `NOT` |
| տեքստային | `Conc` | `&` |
| ինդեքսավորման | `Index` | `[]` |

`None`-ը պահուստային արժեք է և վավեր գործողության հանգույցում չպետք է
հանդիպի։


## Արտահայտությունները

Կեռասի ամեն մի արտահայտություն ածանցված է `Expression` դասից.

```cpp
class Expression : public Node {
public:
    Expression(NodeKind kind, Position line)
        : Node{kind, line}
    {
    }

    using Ptr = std::unique_ptr<Expression>;
};
```

`Expression::Ptr` ընդհանուր ցուցիչով կարելի է պահել ցանկացած կոնկրետ
արտահայտություն։ Սա պետք է, օրինակ, `RETURN` հրամանին, որը կարող է վերադարձնել
թե՛ պարզ լիտերալ, թե՛ փոփոխական, թե՛ գործողություններից կազմված մեծ ենթածառ։

Արտահայտությունների հանգույցները կարելի է բաժանել չորս խմբի՝ լիտերալներ,
փոփոխականներ, գործողություններ և ֆունկցիայի կիրառություններ։


### Լիտերալները

Ամենապարզ արտահայտությունները լիտերալներն են։ Ծառը դրանց համար պահում է
ծրագրում բացահայտ գրված արժեքը.

```cpp
class Boolean final : public Expression {
public:
    // ...
    const bool _value{false};
};

class Number final : public Expression {
public:
    // ...
    const double _value{0.0};
};

class Text final : public Expression {
public:
    // ...
    const std::string _value;
};
```

`TRUE` կամ `FALSE` բառույթից կառուցվում է `Boolean` հանգույց, թվային
լիտերալից՝ `Number`, իսկ չակերտների մեջ վերցրած տեքստից՝ `Text`։

`Text`-ի կառուցիչը `std::string_view` է ընդունում, բայց արժեքը պահում է սեփական
`std::string` դաշտում։ Հետևաբար հանգույցը կախված չէ սկզբնական բառույթի կամ
մուտքային հոսքի հիշողությունից։ Նույն սկզբունքը կիրառվում է անուններ պահող
մյուս հանգույցներում։


### Փոփոխականը

Արտահայտության մեջ գրված անունը ներկայացվում է `Variable` հանգույցով.

```cpp
class Variable final : public Expression {
public:
    Variable(std::string_view name, Position line)
        : Expression{NodeKind::Variable, line}
        , _name{name}
    {
    }

    const std::string _name;
};
```

Այս հանգույցը պահում է միայն անունը։ Այն դեռ չի ասում, թե այդ անունը որտեղ է
հայտարարված կամ ինչ տիպ ունի։ Դրանք շարահյուսական հարցեր չեն։ Հաջորդ՝
իմաստային վերլուծության փուլում `Variable` հանգույցի `NodeId`-ն կկապվի
սիմվոլների աղյուսակի համապատասխան գրառմանը։

Օրինակ, `a + a` արտահայտության մեջ կառուցվում են երկու առանձին `Variable`
հանգույցներ։ Դրանց անունները նույնն են, բայց `NodeId` արժեքները՝ տարբեր։
Իմաստային մոդելում երկուսն էլ հետագայում կարող են կապվել նույն փոփոխականի
սիմվոլին։


### Միտեղանի գործողությունը

Միտեղանի գործողությունը պահում է գործողության տեսակն ու միակ օպերանդը.

```cpp
class Unary final : public Expression {
public:
    Unary(Operation operation, Expression::Ptr operand, Position line)
        : Expression{NodeKind::Unary, line}
        , _operation{operation}
        , _operand{std::move(operand)}
    {
    }

    const Operation _operation{Operation::None};
    const Expression::Ptr _operand;
};
```

Կեռասում միտեղանի գործողություններն են `+`, `-` և `NOT`։ Օրինակ,
`-value` արտահայտության համար `_operation`-ը `Operation::Sub` է, իսկ
`_operand`-ը ցույց է տալիս `Variable("value")` հանգույցը։

Մի քանի գործողություն կարող է ներդրվել իրար մեջ։ `NOT NOT ready`
արտահայտությունը մի `Unary` հանգույց է, որի օպերանդը նորից `Unary` հանգույց է։


### Երկտեղանի գործողությունը

Երկտեղանի գործողությունն ունի ձախ ու աջ օպերանդներ.

```cpp
class Binary final : public Expression {
public:
    Binary(Operation operation, Expression::Ptr left,
        Expression::Ptr right, Position line)
        : Expression{NodeKind::Binary, line}
        , _operation{operation}
        , _left{std::move(left)}
        , _right{std::move(right)}
    {
    }

    const Operation _operation{Operation::None};
    const Expression::Ptr _left;
    const Expression::Ptr _right;
};
```

Այս մեկ հանգույցով ներկայացվում են թվաբանական, տրամաբանական, տեքստային ու
համեմատման բոլոր երկտեղանի գործողությունները։ Օրինակ, `a + b * c`
արտահայտության ծառի գագաթը գումարումն է, իսկ աջ զավակը՝ բազմապատկումը.

```text
       Add
      /   \
     a    Mul
         /   \
        b     c
```

Այս կառուցվածքն արդեն բացահայտ պահում է գործողությունների նախապատվությունը։
Հաջորդ փուլերին հարկավոր չէ նորից հիշել, որ բազմապատկումն ավելի բարձր
նախապատվություն ունի, քան գումարումը. ճիշտ հերթականությունը մարմնավորված է
ծառի ձևում։

Զանգվածի տարրին դիմելու գործողությունն էլ ներկայացվում է `Binary` հանգույցով։
`values[index]` գրառման համար գործողությունը `Operation::Index` է, ձախ
օպերանդը `values` փոփոխականը, իսկ աջը՝ `index` արտահայտությունը։ Թե արդյոք
ձախ կողմն իսկապես զանգված է, իսկ ինդեքսը՝ թվային արժեք, ստուգվում է իմաստային
վերլուծության ժամանակ։


### Ֆունկցիայի կիրառությունը

Արտահայտության մեջ ենթածրագրի կիրառությունը ներկայացնում է `Apply` հանգույցը.

```cpp
class Apply final : public Expression {
public:
    Apply(std::string_view callee,
        std::vector<Expression::Ptr> arguments,
        Position line)
        : Expression{NodeKind::Apply, line}
        , _callee{callee}
        , _arguments{std::move(arguments)}
    {
    }

    const std::string _callee;
    const std::vector<Expression::Ptr> _arguments;
};
```

`_callee` դաշտը կիրառվող ֆունկցիայի անունն է, իսկ `_arguments`-ը՝ արգումենտների
արտահայտությունների ցուցակը։ Օրինակ,

```basic
SQR(a^2 + b^2)
```

գրառման `Apply` հանգույցի անունը `SQR` է, իսկ միակ արգումենտը գումարման
`Binary` ենթածառն է։

Նորից նկատենք, որ այստեղ պահվում է միայն կանչվողի անունը։ Արդյոք այդ անունով
ֆունկցիա հայտարարված է, քանի պարամետր ունի և ինչ տիպ է վերադարձնում՝ կորոշվի
իմաստային վերլուծության ժամանակ։


## Տիպերի հանգույցները

Կեռասի հայտարարումներում տիպը շարահյուսության բացահայտ մաս է։ Ուրեմն այն
նույնպես ներկայացվում է AST հանգույցով։ Բոլոր տիպերի հիմքը `Type` վերացական
դասն է.

```cpp
class Type : public Node {
public:
    using Ptr = std::unique_ptr<Type>;

    bool isArray() const noexcept
    {
        return kind == NodeKind::ArrayType;
    }

    virtual const ScalarType& base() const noexcept = 0;

protected:
    Type(NodeKind kind, Position line)
        : Node{kind, line}
    {
    }
};
```

`isArray()` մեթոդը տարբերակում է պարզ ու զանգվածային տիպերը, իսկ `base()`-ը
վերադարձնում է դրանց բազային պարզ տիպը։


### Պարզ տիպերը

`ScalarType` հանգույցը ներկայացնում է `REAL`, `TEXT` և `BOOL` տիպերը.

```cpp
class ScalarType final : public Type {
public:
    enum class Name {
        Real,
        Text,
        Bool,
    };

    // ...

    const ScalarType& base() const noexcept override
    {
        return *this;
    }

    const Name _name;
};
```

Պարզ տիպի բազային տիպը հենց ինքն է, ուստի `base()`-ը վերադարձնում է `*this`։
`_name` դաշտն արդեն տարբերակում է երեք հնարավոր անունները։


### Զանգվածային տիպերը

Զանգվածի տիպը պահում է տարրերի պարզ տիպն ու չափի արտահայտությունը.

```cpp
class ArrayType final : public Type {
public:
    // ...

    const ScalarType& base() const noexcept override
    {
        return *_base;
    }

    bool isOpen() const noexcept
    {
        return _size == nullptr;
    }

    const ScalarType::Ptr _base;
    const Expression::Ptr _size;
};
```

Օրինակ,

```basic
DIM names[10] AS TEXT
```

հայտարարության տիպը `ArrayType` է։ `_base` դաշտը ցույց է տալիս
`ScalarType::Text` հանգույցը, իսկ `_size`-ը՝ 10 արժեքով `Number`
արտահայտությունը։ Չափը հենց արտահայտություն է, որովհետև Կեռասում թույլատրելի է
նաև այսպիսի հայտարարում.

```basic
DIM values[count * 2] AS REAL
```

Պարամետրի զանգվածը չափ չունի.

```basic
SUB PrintAll(values[] AS TEXT)
    ' ...
END SUB
```

Այս դեպքում `ArrayType::_size`-ը `nullptr` է, իսկ `isOpen()` մեթոդը
վերադարձնում է `true`։ Այդպիսի տիպն անվանում ենք _բաց զանգվածային տիպ_։
Տեղային հայտարարության չափով տիպը, համապատասխանաբար, փակ է։

Երկու տիպերի հավասարությունը սահմանված է `operator==` գործողությամբ.

```cpp
inline bool operator==(const Type& left, const Type& right) noexcept
{
    return left.isArray() == right.isArray()
        && left.base()._name == right.base()._name;
}
```

Համեմատվում են պարզ կամ զանգվածային ձևն ու բազային տիպը։ Զանգվածի չափը տիպային
հավասարության մաս չէ։ Օրինակ, `TEXT[10]` ու `TEXT[20]` հայտարարումները
ներկայացնող տիպերը հավասար են, որովհետև երկուսն էլ `TEXT` տարրերի զանգված են։


## Հրամանները

Բոլոր հրամաններն ածանցված են `Statement` դասից.

```cpp
class Statement : public Node {
public:
    Statement(NodeKind kind, Position line)
        : Node{kind, line}
    {
    }

    using Ptr = std::unique_ptr<Statement>;
};
```

`Statement::Ptr`-ը թույլ է տալիս մեկ ցուցակում պահել տարբեր տեսակի հրամաններ։
Այդ հնարավորությունն օգտագործում է `Sequence` հանգույցը։


### Հրամանների հաջորդականությունը

Ենթածրագրի, ցիկլի կամ պայմանական ճյուղի մարմինը հրամանների հերթականություն է.

```cpp
class Sequence final : public Node {
public:
    Sequence(std::vector<Statement::Ptr> items, Position line)
        : Node{NodeKind::Sequence, line}
        , _items{std::move(items)}
    {
    }

    const std::vector<Statement::Ptr> _items;
};
```

`Sequence`-ն ինքը `Statement`-ից ածանցված չէ։ Այն կառուցվածքային հանգույց է,
որը պահում է մարմնի հրամանները։ `_items` վեկտորի հերթականությունը նույնն է, ինչ
սկզբնական ծրագրում. հետագա կատարման կամ կոդի գեներացիայի փուլը հրամաններն այդ
կարգով է մշակելու։

Դատարկ մարմինը ներկայացվում է դատարկ `_items` վեկտորով։ Առանձին «դատարկ
հրամանի» հանգույց պետք չէ։


### Հայտարարումը

`DIM` հայտարարումը ներկայացնում է `Dim` հանգույցը.

```cpp
class Dim final : public Statement {
public:
    Dim(std::string_view name, Type::Ptr type, Position line)
        : Statement{NodeKind::Dim, line}
        , _name{name}
        , _type{std::move(type)}
    {
    }

    const std::string _name;
    const Type::Ptr _type;
};

using Parameter = Dim;
```

Հանգույցը պահում է հայտարարվող անունն ու նրա տիպը։ Պարզ փոփոխականի դեպքում
`_type`-ը ցույց է տալիս `ScalarType`, իսկ զանգվածի դեպքում՝ `ArrayType`։

Ենթածրագրի պարամետրը շարահյուսորեն նույնպես անուն ու տիպ ունեցող հայտարարում
է։ Այդ պատճառով առանձին, նույն դաշտերը կրկնող դաս չենք սահմանել.
`Parameter`-ը `Dim`-ի alias-ն է։ Պարամետրի ու տեղային հայտարարության դերը
տարբերակվում է այն տեղով, որտեղ հանգույցը պահվում է՝ ենթածրագրի պարամետրերի
ցուցակում կամ մարմնի հրամանների մեջ։


### Վերագրումը

`LET` հրամանը պահում է նպատակային փոփոխականը, ընտրովի ինդեքսն ու վերագրվող
արժեքը.

```cpp
class Let final : public Statement {
public:
    // ...

    const Variable::Ptr _variable;
    const Expression::Ptr _index;
    const Expression::Ptr _value;
};
```

Պարզ վերագրման դեպքում `_index`-ը դատարկ է.

```basic
LET total = 42
```

Իսկ զանգվածի տարրին վերագրելիս այն պահում է ինդեքսի արտահայտությունը.

```basic
LET names[index + 1] = "Cherry"
```

Ինչո՞ւ վերագրման ձախ մասը չի ներկայացվում նույն `Binary(Index)` հանգույցով,
ինչ սովորական `names[index]` արտահայտությունը։ `LET`-ի շարահյուսությունը ձախ
կողմում պահանջում է կոնկրետ անուն և առավելագույնը մեկ ինդեքս։ Այդ կառուցվածքը
`_variable` ու `_index` դաշտերով ներկայացնելը թույլ է տալիս հետագա փուլերին
անմիջապես ստանալ վերագրման նպատակային փոփոխականը։


### Ճյուղավորումը

`IF` կառուցվածքը կարող է ունենալ մեկից ավելի պայմանով ճյուղ և ընտրովի
`ELSE` այլընտրանք։ Պայմանով մեկ ճյուղը ներկայացվում է `IfBranch` հանգույցով.

```cpp
class IfBranch final : public Node {
public:
    // ...

    const Expression::Ptr _condition;
    const Sequence::Ptr _body;
};
```

Այն `Statement` չէ, որովհետև ինքնուրույն հրաման չի հանդիսանում։ `IfBranch`-ը
`If` հրամանի բաղադրիչն է և պահում է միայն պայմանն ու տվյալ պայմանի համար
կատարվող մարմինը։

`If` հանգույցն արդեն պահում է ճյուղերի ցուցակն ու ընտրովի այլընտրանքը.

```cpp
class If final : public Statement {
public:
    // ...

    const std::vector<IfBranch::Ptr> _branches;
    const Sequence::Ptr _alternative;
};
```

Առաջին տարրը `IF` ճյուղն է, իսկ հաջորդները՝ `ELSEIF` ճյուղերը։ `ELSE`-ը
պայման չունի, ուստի ներկայացվում է միայն `Sequence` ցուցիչով։ Եթե `ELSE`
բացակայում է, `_alternative`-ը `nullptr` է։

Այս ներկայացումն ուղղակիորեն պահպանում է Կեռասի գրառման կառուցվածքը և չի
վերածում `ELSEIF`-երը իրար մեջ ներդրված `IF` հանգույցների։


### Նախապայմանով ցիկլը

`WHILE` հրամանին անհրաժեշտ է կրկնության պայմանն ու մարմինը.

```cpp
class While final : public Statement {
public:
    // ...

    const Expression::Ptr _condition;
    const Sequence::Ptr _body;
};
```

AST-ը չի պահանջում, որ `_condition`-ը տրամաբանական տիպ ունենա։ Այն ընդամենը
պահում է parser-ի կարդացած արտահայտությունը։ Տիպային պահանջը ստուգվելու է
իմաստային փուլում։


### Հաշվիչով ցիկլը

`FOR` հանգույցը պահում է հաշվիչը, սկզբնական ու վերջնական արտահայտությունները,
քայլը և մարմինը.

```cpp
class For final : public Statement {
public:
    // ...

    const Variable::Ptr _parameter;
    const Expression::Ptr _begin;
    const Expression::Ptr _end;
    const Number::Ptr _step;
    const Sequence::Ptr _body;
};
```

Հաշվիչը կարող է միայն փոփոխական լինել, այդ պատճառով `_parameter` դաշտի տիպը
`Variable::Ptr` է։ Սկզբնական ու վերջնական արժեքները ընդհանուր
արտահայտություններ են։

Քայլի տիպը հատուկ `Number::Ptr` է, ոչ թե `Expression::Ptr`։ Սա բխում է
Կեռասի քերականությունից. `STEP`-ից հետո թույլատրվում է միայն ընտրովի նշանով
թվային լիտերալ։ Եթե `STEP`-ը գրված չէ, parser-ն ինքն է ստեղծում 1 արժեքով
`Number` հանգույց։


### Պրոցեդուրայի կանչը

Պրոցեդուրայի կանչը ներկայացվում է `Call` հանգույցով.

```cpp
class Call final : public Statement {
public:
    // ...

    const std::string _callee;
    const std::vector<Expression::Ptr> _arguments;
};
```

Կառուցվածքով այն նման է `Apply`-ին. երկուսն էլ պահում են անուն ու արգումենտների
ցուցակ։ Բայց `Apply`-ը `Expression` է և օգտագործվում է արժեք ակնկալող
արտահայտության մեջ, իսկ `Call`-ը `Statement` է և ներկայացնում է ինքնուրույն
հրաման։

Այս բաժանումը հետագայում թույլ է տալիս իմաստային վերլուծիչին հստակ պահանջել,
որ `CALL`-ով կանչվի միայն պրոցեդուրա, իսկ `Apply`-ով՝ արժեք վերադարձնող
ֆունկցիա։


### Արժեքի վերադարձը

`RETURN` հրամանի հանգույցը պահում է վերադարձվող արտահայտությունը.

```cpp
class Return final : public Statement {
public:
    Return(Expression::Ptr value, Position line)
        : Statement{NodeKind::Return, line}
        , _value{std::move(value)}
    {
    }

    const Expression::Ptr _value;
};
```

Այստեղ էլ ծառը չի ստուգում, թե հրամանը ֆունկցիայի մարմնո՞ւմ է, և արդյոք
արտահայտության տիպը համապատասխանո՞ւմ է վերադարձվող տիպին։ AST-ի խնդիրը
կառուցվածքը պահելն է։ Դրա ճիշտ իմաստը ստուգում է հաջորդ փուլը։


## Ենթածրագիրն ու ծրագիրը

Կեռասի ենթածրագիրը միավորում է անունը, պարամետրերը, ընտրովի վերադարձվող տիպն
ու մարմինը.

```cpp
class Subroutine final : public Node {
public:
    // ...

    const std::string _name;
    const std::vector<Parameter::Ptr> _parameters;
    const ScalarType::Ptr _returnType;
    const Sequence::Ptr _body;
};
```

`_returnType`-ի դատարկ լինելը նշանակում է, որ ենթածրագիրը պրոցեդուրա է։ Եթե
այն ցույց է տալիս `ScalarType` հանգույց, ապա ենթածրագիրը ֆունկցիա է։ Կեռասի
ֆունկցիան կարող է վերադարձնել միայն պարզ արժեք, այդ պատճառով վերադարձվող
տիպը `ScalarType::Ptr` է, ոչ թե ընդհանուր `Type::Ptr`։

Պարամետրերի հերթականությունը պահպանվում է `_parameters` վեկտորում։ Կանչի
արգումենտներն իմաստային վերլուծության ժամանակ դրանց են համապատասխանեցվելու
ըստ դիրքի։ Մարմինը մեկ `Sequence` հանգույց է։

Ամբողջ ծառի արմատը `Program`-ն է.

```cpp
class Program final : public Node {
public:
    Program(std::vector<Subroutine::Ptr> subroutines, Position line)
        : Node{NodeKind::Program, line}
        , _subroutines{std::move(subroutines)}
    {
    }

    const std::vector<Subroutine::Ptr> _subroutines;
};
```

`Program`-ը պահում է ենթածրագրերը սկզբնական ֆայլում հանդիպած հերթականությամբ։
Այստեղ դրանք անունից հանգույց արտապատկերող աղյուսակում չեն պահվում։ Կրկնվող
անունների հայտնաբերումն ու կանչերի կապումը շարահյուսական ծառի գործը չէ.
դրանցով զբաղվում է սիմվոլների աղյուսակը։

Դատարկ ֆայլից կառուցվում է ենթածրագրերի դատարկ ցուցակով `Program` հանգույց։
Արդյոք կատարվող ծրագիրն ունի պարտադիր `Main` ենթածրագիրը՝ նույնպես
իմաստային ստուգում է։


## Ծառով անցնելը

Ծառը կառուցելուց հետո կոմպիլյատորի տարբեր փուլեր պետք է անցնեն դրա
հանգույցներով։ Օրինակ, Lisp ներկայացումը պետք է ամեն հանգույցից տեքստ
կառուցի, անունների լուծման անցումը՝ փոփոխականներն ու ենթածրագրերը կապի
սիմվոլներին, իսկ տիպերի ստուգման անցումը՝ հաշվարկի արտահայտությունների տիպերը։

Կարելի էր ամեն անգամ գրել մեծ `switch` և կրկնել `NodeKind`-ի բոլոր դեպքերը։
Այդ ընդհանուր դիսպետչերացումը մեկ տեղում կենտրոնացնելու համար սահմանված է
`ASTVisitor` կաղապարային դասը.

```cpp
template<typename Derived, typename ReturnType = void>
class ASTVisitor {
protected:
    ReturnType visit(Node& value)
    {
        switch( value.kind ) {
            case NodeKind::Program:
                return derived().visit(
                    static_cast<Program&>(value));
            case NodeKind::Subroutine:
                return derived().visit(
                    static_cast<Subroutine&>(value));
            // ... մնացած հանգույցները
            case NodeKind::Empty:
                return ReturnType{};
        }

        return ReturnType{};
    }

private:
    Derived& derived()
    {
        return static_cast<Derived&>(*this);
    }
};
```

`ASTVisitor`-ը պարամետրացվում է ածանցյալ մշակողի տիպով և վերադարձվող արժեքի
տիպով։ Օրինակ, տեքստ կառուցող այցելուի `ReturnType`-ը `std::string` է, իսկ
իմաստային անցումներինը լռելությամբ `void`։

`visit(Node&)` մեթոդը նայում է `kind` դաշտին, հղումը փոխակերպում կոնկրետ
տիպի և կանչում ածանցյալ դասի նույն տիպն ընդունող `visit()` տարբերակը։ Այս
մոտեցումը հայտնի է որպես CRTP՝ curiously recurring template pattern։
Վիրտուալ `visit()` մեթոդների աղյուսակ պետք չէ, իսկ կոնկրետ հանգույցների դասերը
չեն ծանրաբեռնվում տարբեր անցումների վարքով։

Նկատենք մի կարևոր բան. բազային `ASTVisitor`-ը միայն ընտրում է ճիշտ մեթոդը,
բայց ինքնաբերաբար չի անցնում հանգույցի զավակներով։ Ամեն կոնկրետ այցելու ինքն է
որոշում անցման կարգը։ Օրինակ, `Binary` հանգույցի համար մեկը կարող է նախ
այցելել ձախ, ապա աջ օպերանդը, իսկ մի ուրիշ վերլուծություն՝ միայն անհրաժեշտ
ճյուղը։

`NodeKind::Empty` արժեքի համար վերադարձվում է `ReturnType{}`։ `void` դեպքում
դա պարզապես ավարտ է, իսկ `std::string`-ի դեպքում՝ դատարկ տող։


## Ծառի Lisp ներկայացումը

Ծրագրի ծառը հիշողության մեջ դիտելը հարմար չէ։ Parser-ը մշակելիս կամ
գործողությունների նախապատվությունը ստուգելիս օգտակար է ունենալ դրա պարզ
տեքստային ներկայացումը։ Այդ նպատակով սահմանված է `AstLisp` դասը։

`AstLisp`-ը `ASTVisitor<AstLisp, std::string>`-ից ածանցված այցելու է։ Ամեն
հանգույցի համար նրա `visit()` մեթոդը վերադարձնում է Lisp-ի նման ցուցակ։
Օրինակ.

```cpp
std::string AstLisp::visit(Binary& node)
{
    return std::format(
        "(avium-binary :operation \"{}\" :left {} :right {})",
        node._operation,
        visit(*node._left),
        visit(*node._right));
}
```

Մեթոդը նախ ռեկուրսիվ ստանում է երկու օպերանդների ներկայացումները, ապա դրանք
տեղադրում ընթացիկ հանգույցի տեքստում։ `Sequence`-ների, արգումենտների ու
պարամետրերի վեկտորները մշակվում են ընդհանուր `visitVector()` մեթոդով։

Դիտարկենք հետևյալ ծրագիրը.

```basic
SUB Main
    DIM result AS REAL
    LET result = 1 + 2
END SUB
```

`AstLisp::emit()` մեթոդի արդյունքը մեկ տողով այսպիսին է.

```lisp
(avium-program :subroutines (avium-subroutine :name "Main" :parameters '() :return-type NIL :body (avium-sequence :items (avium-dim :name "result" :type (avium-scalar-type :name "REAL")) (avium-let (avium-variable :name "result") :value (avium-binary :operation "+" :left (avium-number :value 1) :right (avium-number :value 2))))))
```

Արտաքին `avium-program` ցուցակը պարունակում է `avium-subroutine`, դրա մարմինը՝
`avium-sequence`, այն՝ `avium-let`, իսկ վերագրվող արժեքի տակ երևում է
գումարման `avium-binary` հանգույցը։ Փակագծերի ներդրվածությունը նույնությամբ
արտացոլում է ծառի ծնող-զավակ կապերը։

Պարզ տիպը ներկայացվում է `avium-scalar-type` ցուցակով։ Զանգվածային տիպի
ներկայացման մեջ առանձին երևում են բազային տիպն ու չափը։ Բաց զանգվածի
`:size` արժեքը `NIL` է։ Նույն կերպ պրոցեդուրայի `:return-type`-ը `NIL` է,
իսկ ֆունկցիայինը՝ համապատասխան պարզ տիպի ցուցակը։

`AstLisp::emit()`-ը հանրային հոսքին ավելացնում է նաև նոր տողի նիշ։ Դասի հին
`Lisper` անունը պահպանված է որպես alias.

```cpp
using Lisper = AstLisp;
```

Այս տեքստային ձևը նախատեսված է առաջին հերթին ծառը տեսնելու և թեստերում
համեմատելու համար։ Այն չի փոխարինում բուն AST օբյեկտներին և կոմպիլյատորի
հաջորդ փուլերը Lisp տեքստ չեն վերլուծում։


## Ինչ չի պահվում ծառում

Արժե մեկ անգամ ևս հստակեցնել AST-ի պատասխանատվության սահմանը։ Այն պահում է
ծրագրի շարահյուսական կառուցվածքը, բայց չի պատասխանում հետևյալ հարցերին.

* արդյո՞ք փոփոխականի անունը հայտարարված է,
* նույն անունով ո՞ր հայտարարումն է տեսանելի տվյալ կետում,
* ի՞նչ տիպ ունի `a + b` արտահայտությունը,
* ֆունկցիայի կանչի արգումենտները համապատասխանո՞ւմ են պարամետրերին,
* ունի՞ ծրագիրը ճիշտ `Main` մուտքի կետ։

Օրինակ, `Variable` հանգույցն ունի անուն, բայց չունի սիմվոլի ցուցիչ։
`Binary` հանգույցն ունի գործողություն ու օպերանդներ, բայց չունի արդյունքի
տիպի դաշտ։ `Apply`-ն ունի կանչվող անուն, բայց չունի ստորագրություն։

Սա թերություն չէ, այլ ճարտարապետական ընտրություն։ Շարահյուսական ծառը մնում է
պարզ ու կայուն, իսկ իմաստային տեղեկությունները հաշվարկվում են հաջորդ փուլում և
պահվում առանձին մոդելում։ Նույն ծառը հնարավոր է օգտագործել տարբեր
վերլուծությունների կամ կոդի գեներացիայի տարբեր եղանակների համար։


## Թեստերը

AST հանգույցների թեստերը գրված են `tests/ast_test.cxx` ֆայլում։ Դրանք ստուգում
են հանգույցի տեսակը, տողն ու եզակի համարը, պարզ և կազմական
արտահայտությունները, բաց ու փակ զանգվածային տիպերը, հայտարարումները,
վերագրումները, ղեկավարող կառուցվածքները, կանչերը, վերադարձը, ենթածրագրերն ու
ամբողջ ծրագիրը։

Առանձին թեստով հաստատվում է, որ `Parameter`-ը հենց `Dim`-ի alias-ն է։ Մեկ այլ
թեստ կառուցում է տարբեր տիպերի հանգույցներ և համոզվում, որ `ASTVisitor`-ը
`NodeKind` արժեքով կանչում է ճիշտ `visit()` տարբերակը։

`tests/astlisp_test.cxx` ֆայլում ստուգվում է ծառի Lisp ներկայացումը։ Թեստերը
ներառում են դատարկ ծրագիրը, պարզ ու զանգվածային տիպերը, արտահայտություններն ու
հրամանները, կանչերը, ինդեքսավորված վերագրումը և `RETURN` հանգույցը։

Ամբողջ նախագիծը կարելի է կառուցել ու փորձարկել հետևյալ հրամաններով.

```bash
$ cmake -S . -B build
$ cmake --build build
$ ctest --test-dir build --output-on-failure
```

Այս գլխում կառուցված AST-ը Կեռասի կոմպիլյատորի փուլերը կապող ընդհանուր լեզուն
է։ Հաջորդ գլխում scanner-ն ու parser-ը ծրագրի տեքստից կստեղծեն հենց այս
հանգույցները։ Դրանից հետո իմաստային վերլուծիչը նույն ծառով անցնելով կկապի
անունները, կհաշվի արտահայտությունների տիպերն ու կպատրաստի ծրագիրը կոդի
գեներացիայի համար։
