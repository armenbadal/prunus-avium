# Շարահյուսական վերլուծություն

Նախորդ գլուխներում սահմանեցինք Կեռաս լեզվի շարահյուսությունն ու այն տվյալների
կառուցվածքները, որոնցով ծրագիրը ներկայացվում է որպես վերացական շարահյուսական
ծառ։ Բայց լեզվի ձևական նկարագրությունն ինքնին դեռ ծրագիր չէ։ Մեզ անհրաժեշտ է
մի գործիք, որը կկարդա Կեռաս լեզվով գրված տեքստը և դրանից կկառուցի այդ ծառը։

Դիտարկենք մի պարզ ծրագիր.

```basic
SUB Main
    DIM radius AS REAL
    LET radius = 2.5
    CALL Print radius^2
END SUB
```

Մարդու համար այստեղ անմիջապես տեսանելի են `Main` ենթածրագիրը, երեք հրամանները,
`radius^2` արտահայտությունն ու աստիճան բարձրացնելու գործողությունը։ Բայց
կոմպիլյատորը սկզբում տեսնում է միայն նիշերի հոսք.

```text
S U B ␣ M a i n ↵ ␣ ␣ ␣ ␣ D I M ␣ r a d i u s ...
```

Այդ նիշերից միանգամից ծառ կառուցելը հնարավոր է, բայց անհարմար։ Ավելի պարզ է
աշխատանքը բաժանել երկու մասի։ Նախ _բառային վերլուծիչը_՝ `Scanner`-ը, նիշերի
հոսքից առանձնացնում է լեզվի բառերը, լիտերալներն ու գործողությունների նշանները։
Ապա բուն _շարահյուսական վերլուծիչը_՝ `Parser`-ը, այդ տարրերի հաջորդականությունից
ճանաչում է լեզվական կառուցվածքներն ու կառուցում դրանց AST հանգույցները։

Վերը բերված ծրագրի սկիզբը բառային վերլուծությունից հետո կունենա մոտավորապես
այս տեսքը.

| Բառային տարր | Պիտակ |
|:-------------|:------|
| `SUB` | `Token::Subroutine` |
| `Main` | `Token::Identifier` |
| `↵` | `Token::NewLine` |
| `DIM` | `Token::Dim` |
| `radius` | `Token::Identifier` |
| `AS` | `Token::As` |
| `REAL` | `Token::Real` |

Այնուհետև parser-ը `SUB`-ով ճանաչում է ենթածրագրի սկիզբը, `DIM`-ով՝
հայտարարումը, `CALL`-ով՝ պրոցեդուրայի կանչը, իսկ `radius^2` հաջորդականությունից
կառուցում է `Binary` հանգույց։

Ընդհանուր ընթացքը կարելի է պատկերել այսպես.

```text
Ծրագրի տեքստ
      |
      v
   Scanner  -->  Lexeme-ների հոսք
                       |
                       v
                    Parser  -->  Program AST
                       |
                       +----->  Diagnostics
```

`Scanner`-ը սխալ բառույթի համար վերադարձնում է `Token::None` պիտակով տարր։
Դրանից արդեն parser-ն է ախտորոշում կառուցում։ Նույն `Diagnostics` օբյեկտում
կուտակվում են նաև բացակայող կամ սխալ տեղում հանդիպած շարահյուսական տարրերի
մասին հաղորդագրությունները։ Եթե սխալներ չկան, կառուցված `Program` ծառը կարելի
է փոխանցել հաջորդ՝ իմաստային վերլուծության փուլին։


## Բառային տարրերն ու դրանց պիտակները

Բառային վերլուծիչի ու parser-ի հաղորդակցման լեզուն `Lexeme` դասն է։ Դրա ամեն
մի օբյեկտ պահում է երեք արժեք.

```cpp
class Lexeme {
public:
    Token kind = Token::None;
    std::string value;
    unsigned int line = 0;

    // ...
};
```

`kind` դաշտը բառային տարրի _պիտակն_ է, `value`-ն՝ ծրագրում հանդիպած տեքստը,
իսկ `line`-ը՝ տողի համարը։ Օրինակ, ծրագրի երկրորդ տողի `radius` անունից
կստեղծվի այսպիսի օբյեկտ.

```cpp
Lexeme{Token::Identifier, "radius", 2}
```

`Token` թվարկման մեջ հավաքված են Կեռասի բոլոր բառային կատեգորիաները։ Դրանք
կարելի է պայմանականորեն բաժանել մի քանի խմբի.

* նույնացուցիչներ ու լիտերալներ՝ `Identifier`, `RealLit`, `TextLit`,
  `BoolLit`,
* ծառայողական բառեր՝ `Subroutine`, `Dim`, `Let`, `If`, `While` և մյուսները,
* տիպերի անուններ՝ `Real`, `Text`, `Bool`,
* գործողություններ՝ `Add`, `Mul`, `Eq`, `And`, `Not` և այլն,
* կետադրական տարրեր՝ փակագծեր ու ստորակետ,
* տողի ու ֆայլի սահմաններ՝ `NewLine` և `Eof`,
* սխալ բառույթի `None` նշիչը։

`Lexeme::is()` մեթոդը ստուգում է՝ արդյոք տարրն ունի սպասվող պիտակը։ Մեթոդն ունի
նաև մի քանի այլընտրանք ընդունող տարբերակ, ուստի

```cpp
lexeme.is(Token::Real, Token::Text, Token::Bool)
```

գրառմամբ կարելի է մեկ անգամից ստուգել տիպի բոլոր երեք անունները։

Այսպիսով, `Lexeme`-ը կապող օղակ է։ Scanner-ը չգիտի, թե իր կարդացած `IF` բառով
ինչպիսի ծառ է կառուցվելու, իսկ parser-ը չգիտի, թե այդ բառի երեք նիշերն ինչպես
են կարդացվել հոսքից։ Երկուսն էլ գիտեն միայն, թե ինչ է նշանակում
`Token::If` պիտակով բառային տարրը։


## Բառային վերլուծիչը

`Scanner` դասի արտաքին ինտերֆեյսը միտումնավոր փոքր է.

```cpp
class Scanner {
public:
    explicit Scanner(std::istream& source);

    Lexeme scan();

private:
    Lexeme scanNumber();
    Lexeme scanText();
    Lexeme scanIdentifier();

    std::istream& _source;
    unsigned int _line{1};
};
```

Կառուցման ժամանակ scanner-ին փոխանցվում է ծրագրի տեքստը կարդացող հոսքը։
`scan()` մեթոդի ամեն մի կանչ վերադարձնում է այդ հոսքի հերթական բառային տարրը։
`_line` դաշտը պահում է ընթացիկ տողի համարը և սկզբում ունի `1` արժեքը։

Սովորաբար ձևաչափված ներմուծման հոսքը բացատանիշերն ինքնաբերաբար կարող է բաց
թողնել։ Մեզ դա հարմար չէ, որովհետև նոր տողի նիշն ինքնուրույն բառային տարր է։
Այդ պատճառով կառուցիչում անջատվում է `skipws` ռեժիմը.

```cpp
Scanner::Scanner(std::istream& source)
    : _source{source}
{
    _source.unsetf(std::ios_base::skipws);
}
```

Հիմա արդեն հոսքի ամեն մի նիշ վերահսկվում է հենց մեր scanner-ի կողմից։


### Օժանդակ պրեդիկատներն ու `readWhile()`-ը

Թիվը կամ նույնացուցիչը կարդալիս պետք է հոսքից վերցնել իրար հաջորդող նիշերը
այնքան ժամանակ, քանի դեռ դրանք բավարարում են որևէ պայմանի։ Այդ ընդհանուր
գործողությունն առանձնացված է `readWhile()` ֆունկցիայում.

```cpp
template<typename Predicate>
    requires std::predicate<Predicate, char>
std::string readWhile(std::istream& input, Predicate predicate)
{
    std::string result;
    char value{};
    while( input.get(value) ) {
        if( !predicate(value) ) {
            input.unget();
            break;
        }
        result += value;
    }
    return result;
}
```

Ֆունկցիան հերթական նիշը կարդում և ավելացնում է արդյունքին, քանի դեռ
`predicate` պայմանը ճշմարիտ է։ Առաջին անհամապատասխան նիշը `unget()`-ով
վերադարձվում է հոսքին։ Այն չի կորչում. հաջորդ բառային տարրը ճանաչելիս scanner-ը
նորից կդիտարկի հենց այդ նիշը։

Նույնացուցիչների համար սահմանված են երկու պրեդիկատներ.
`isIdentifierStart()`-ը թույլ է տալիս տառ, իսկ `isIdentifierPart()`-ը՝ տառ կամ
թվանշան։ Այս տարբերակումը պետք է, որովհետև Կեռասում անունը կարող է թվանշան
պարունակել, բայց չի կարող թվանշանով սկսվել։


### `scan()` մեթոդի ընտրությունը

`scan()` մեթոդը նախ բաց է թողնում սովորական բացատները՝ `' '`, `'\t'` և `'\r'`։
Նոր տողի `'\n'` նիշն այստեղ միտումնավոր բաց չի թողնվում։ Ապա դիտարկվում է
հոսքի հերթական նիշն ու ընտրվում համապատասխան ճանաչող մեթոդը.

```cpp
const auto next = _source.peek();
if( next == std::char_traits<char>::eof() )
    return {Token::Eof, "EOF", _line};

const auto value = static_cast<char>(next);

if( isDigit(value) )
    return scanNumber();

if( value == '"' )
    return scanText();

if( isIdentifierStart(value) )
    return scanIdentifier();
```

Թվանշանը տանում է `scanNumber()` մեթոդին, չակերտը՝ `scanText()`-ին, իսկ տառը՝
`scanIdentifier()`-ին։ Եթե հերթական նիշը նոր տող է, այն սպառվում է, վերադարձվում
`Token::NewLine`, ապա `_line`-ն ավելացվում է մեկով։

Մնացած նիշերից `<`-ն ու `>`-ը մշակվում են առանձին, որովհետև դրանցով սկսվում են
նաև երկնիշ գործողություններ՝ `<>`, `<=` և `>=`։ Վերջում մեկ նիշից կազմված
փակագծերը, ստորակետն ու գործողությունները ճանաչվում են
`singleCharacterToken()` ֆունկցիայով։


### Թվային լիտերալները

Կեռասի թվային լիտերալը համապատասխանում է հետևյալ կանոնավոր արտահայտությանը.

```text
[0-9]+(\.[0-9]+)?
```

Նախ կարդացվում են ամբողջ մասի թվանշանները։ Եթե հաջորդ նիշը կետ է, scanner-ը
կարդում է նաև այն և պահանջում առնվազն մեկ թվանշան կոտորակային մասի համար։

```cpp
auto value = readWhile(_source, isDigit);

if( _source.peek() == '.' ) {
    _source.get();
    value += '.';

    const auto next = _source.peek();
    if( next == std::char_traits<char>::eof()
        || !isDigit(static_cast<char>(next)) )
        return {Token::None, value, line};

    value += readWhile(_source, isDigit);
}
```

Ուրեմն `12`, `3.14` և `2026` գրառումները թվային լիտերալներ են, իսկ `12.`-ը՝
սխալ բառույթ։ Բացասական թիվն էլ առանձին լիտերալ չէ. `-12.5` գրառումը scanner-ը
վերադարձնում է որպես `-` գործողություն և `12.5` լիտերալ։ Դրանք մեկ
արտահայտության են միավորվում parser-ի փուլում։


### Տեքստային լիտերալները

Տեքստը սկսվում ու ավարտվում է `"` չակերտով։ Բացող չակերտը բառույթի արժեքի մաս
չի դառնում։ `scanText()`-ը կարդում է ներսի նիշերը մինչև փակող չակերտը.

```cpp
while( _source.get(current) ) {
    if( current == '"' )
        return {Token::TextLit, value, line};

    if( current == '\n' || current == '\r' ) {
        _source.unget();
        return {Token::None, value, line};
    }

    value += current;
}
```

Կեռասի տեքստային լիտերալը չի կարող անցնել նոր տող և escape հաջորդականություններ
չունի։ Եթե փակող չակերտից առաջ նոր տող է հանդիպում, այն վերադարձվում է հոսքին,
իսկ կարդացած տեքստը՝ `Token::None` պիտակով։ Նոր տողը հաջորդ `scan()` կանչով
կվերադարձվի որպես ինքնուրույն տարր։ Նույն `None` արդյունքը ստացվում է, երբ
ֆայլն ավարտվում է առանց փակող չակերտի։


### Նույնացուցիչներն ու ծառայողական բառերը

Նույնացուցիչը սկսվում է տառով և շարունակվում տառերով կամ թվանշաններով։ Scanner-ը
նախ ամբողջ բառը կարդում է որպես սովորական տեքստ։ Ապա ստուգում է՝ արդյոք դա
`TRUE` կամ `FALSE` տրամաբանական լիտերալն է, հետո որոնում է ծառայողական բառերի
`keywords` աղյուսակում։

```cpp
if( value == "TRUE" || value == "FALSE" )
    return {Token::BoolLit, value, line};

const auto keyword = keywords.find(value);
const auto kind =
    keyword == keywords.end() ? Token::Identifier : keyword->second;
return {kind, value, line};
```

`keywords` աղյուսակում են `SUB`, `DIM`, `AS`, `IF`, `RETURN`, `REAL`,
`MOD`, `AND`, `NOT` և լեզվի մյուս ծառայողական բառերը։ Դրանք զգայուն են
տառաչափի նկատմամբ։ `SUB`-ը ծառայողական բառ է, իսկ `Sub`-ն ու `sub`-ը՝ սովորական
նույնացուցիչներ։ Նույն ձևով `TRUE`-ն տրամաբանական լիտերալ է, իսկ `True`-ն՝
անուն։

Ընդգծման `_` նիշը նույնացուցիչի մաս չէ։ Օրինակ, `totalSum2`-ը վավեր անուն է,
իսկ `total_sum` գրառման մեջ scanner-ը `total` նույնացուցիչից հետո `_`-ի համար
սխալ տարր կվերադարձնի։


### Բացատները, մեկնաբանություններն ու նոր տողերը

Կեռասի մեկնաբանությունը սկսվում է ապաթարցով՝ `'`, և շարունակվում է մինչև տողի
վերջը։ `scan()`-ը բացատները բաց թողնելուց հետո ստուգում է հերթական նիշը։ Եթե
այն ապաթարց է, կարդում ու դեն է նետում բոլոր նիշերը մինչև նոր տողը։

```cpp
while( true ) {
    readWhile(_source, isSpace);

    if( _source.peek() != '\'')
        break;

    char value{};
    while( _source.get(value) ) {
        if( value == '\n' ) {
            _source.unget();
            break;
        }
    }
}
```

Նոր տողը մեկնաբանության հետ չի կորչում. այն վերադարձվում է հոսքին և scanner-ի
հաջորդ քայլով դառնում `Token::NewLine`։ Սա կարևոր է, որովհետև Կեռասում նոր
տողը հրամանի ավարտն է։ Դատարկ մեկնաբանության տողը շարահյուսական վերլուծիչի
համար պարզապես դատարկ տող է։

Եթե ֆայլը մեկնաբանությամբ է ավարտվում, հաջորդ արդյունքը ճիշտ ձևով
`Token::Eof` է։


### Գործողություններն ու սխալ նիշերը

Մեկ նիշից կազմված բառային տարրերն են `(`, `)`, `[`, `]`, ստորակետը, `+`,
`-`, `*`, `/`, `\`, `^`, `&` և `=`։ Դրանք ճանաչվում են պարզ `switch`-ով։
`<` ու `>` նշանների համար `scan()`-ը մեկ նիշ առաջ է նայում և, եթե պետք է,
կառուցում `<>`, `<=` կամ `>=` բառույթը։

Եթե նիշը որևէ հայտնի բառային տարրի մաս չէ, `singleCharacterToken()`-ը
վերադարձնում է `Token::None`։ Սխալ նիշը, սակայն, սպառվում է հոսքից։ Դրա
շնորհիվ հաջորդ `scan()` կանչը կարող է շարունակել հաջորդ նիշից և scanner-ը
նույն տեղում անվերջ չի կանգնում։


## Ռեկուրսիվ վայրէջքի վերլուծիչը

Scanner-ից ստացանք բառային տարրերի հոսք։ Հիմա պետք է այդ հարթ
հաջորդականությունից կառուցել ծրագրի ծառային ներկայացումը։ Կեռասի համար
ընտրել ենք _ռեկուրսիվ վայրէջքի_ եղանակը։ Այս մոտեցման հիմնական գաղափարը շատ
պարզ է. քերականության ամեն մի ոչ տերմինալային սիմվոլի համար սահմանվում է այն
վերլուծող մեթոդ։

Օրինակ, ծրագրի կանոնն է.

```ebnf
Program = [ NewLines ] { Subroutine NewLines }.
```

Դրան համապատասխանում է `parseProgram()` մեթոդը։ Նույն կերպ `Subroutine`-ը
վերլուծում է `parseSubroutine()`-ը, `If`-ը՝ `parseIf()`-ը, իսկ
`Addition`-ը՝ `parseAddition()`-ը։

Քերականական կառուցվածքներն էլ գրեթե մեխանիկորեն վերածվում են C++ կոդի։
`[...]` ոչ պարտադիր մասը դառնում է `if` պայման, `{...}` կրկնությունը՝
`while` ցիկլ, իսկ հաջորդաբար գրված տարրերը մշակվում են նույն հերթականությամբ։
Այս նմանությունն է ռեկուրսիվ վայրէջքի կարևոր առավելությունը. կոդը կարդալիս
միշտ կարելի է կողքին դնել քերականական կանոնն ու տեսնել, թե դրա որ մասն է
իրականացվում։

`Parser` դասը հղումներ է պահում scanner-ի ու ախտորոշումների օբյեկտների վրա,
ինչպես նաև մեկ առաջ նայող բառային տարր.

```cpp
class Parser {
public:
    Parser(Scanner& scanner, Diagnostics& diagnostics);

    Program::Ptr parse();

private:
    // վերլուծող մեթոդները

    Scanner& _scanner;
    Diagnostics& _diagnostics;
    Lexeme _lookahead;
};
```

Մեկ `_lookahead` տարրը բավական է որոշելու համար, թե քերականության որ
այլընտրանքն է սկսվում։ Օրինակ, `DIM` պիտակը միարժեք ընտրում է հայտարարումը,
`IF`-ը՝ ճյուղավորումը, իսկ թվային լիտերալը՝ պարզ արտահայտությունը։


## Բառային տարրերի շարժը

Հերթական բառային տարրը կարդում է `advance()` մեթոդը.

```cpp
void Parser::advance()
{
    _lookahead = _scanner.scan();
    _diagnostics.advance();
}
```

Scanner-ից ստացված արժեքը պահվում է `_lookahead` դաշտում։ Միաժամանակ
`Diagnostics` օբյեկտին հայտնում ենք, որ մուտքում առաջընթաց է եղել։ Այս երկրորդ
գործողությունը պետք է սխալների կրկնությունը սահմանափակելու համար. դրան
կվերադառնանք վերականգնման բաժնում։

Երբ քերականությունը պահանջում է կոնկրետ տերմինալային սիմվոլ, օգտագործվում է
`match()` մեթոդը.

```cpp
std::string Parser::match(Token expected)
{
    if( !_lookahead.is(expected) ) {
        _diagnostics.mark(
            _lookahead.line,
            std::format("Սպասվում է '{}', բայց հանդիպել է {}։",
                expected, _lookahead));
        return {};
    }

    auto value = _lookahead.value;
    advance();
    return value;
}
```

Եթե ընթացիկ տարրն ունի սպասվող պիտակը, `match()`-ը պահում է բառույթի արժեքը,
կարդում հաջորդ տարրը և վերադարձնում պահված տեքստը։ Վերադարձված արժեքն
օգտագործվում է նույնացուցիչների ու լիտերալների հանգույցները կառուցելիս։

Իսկ ի՞նչ է լինում, երբ պիտակները չեն համընկնում։ Այդ դեպքում գրանցվում է
սպասված ու փաստացի տարրերը նշող ախտորոշում, վերադարձվում է դատարկ տող, բայց
ընթացիկ տարրը չի սպառվում։ Չսպառելը կարևոր է։ Հանդիպած տարրը կարող է լինել
արտաքին կառուցվածքի սկիզբը կամ ավարտը, ու այն պետք է մշակվի կանչող մեթոդի
կողմից։


## Սկզբնական և համաժամացման բազմությունները

Parser-ի կոդում մի քանի պիտակներ հավաքված են նախապես սահմանված
`std::set` բազմություններում։ Առաջին երկուսը նկարագրում են, թե ինչ տարրով
կարող է սկսվել հրամանը կամ արտահայտությունը.

```cpp
const std::set<Token> firstStatement{
    Token::Let, Token::Dim, Token::If, Token::While,
    Token::For, Token::Call, Token::Return
};

const std::set<Token> firstExpression{
    Token::BoolLit, Token::RealLit, Token::TextLit,
    Token::Identifier, Token::Add, Token::Sub,
    Token::Not, Token::LeftPar
};
```

Սրանք քերականության մեջ հայտնի FIRST բազմությունների գործնական
տարբերակներն են։ Եթե `_lookahead`-ը `firstStatement`-ում է, կարելի է կանչել
`parseStatement()`-ը։ Եթե `firstExpression`-ում է, տվյալ կետից կարող է
արտահայտություն սկսվել։

Մյուս բազմությունները՝ `subroutineSync`, `statementSync` և `expressionSync`,
օգտագործվում են սխալից հետո անվտանգ շարունակության կետ գտնելու համար։
`sequenceEnd`-ն էլ թվարկում է այն տարրերը, որոնցով հրամանների ընթացիկ
հաջորդականությունն ավարտվում է։


## Ծրագիրը և ենթածրագրերը

Վերլուծությունն սկսվում է `Parser::parse()` մեթոդից, որն իր հերթին կանչում է
`parseProgram()`-ը։ Վերջինս նախ `advance()`-ով կարդում է առաջին բառային տարրը
և բաց է թողնում սկզբի դատարկ տողերը։

Այնուհետև մինչև ֆայլի ավարտը պետք է վերլուծվեն միայն ենթածրագրեր։ Եթե վերին
մակարդակում որևէ այլ տարր է հանդիպում, parser-ը բառային տարրեր է բաց թողնում
մինչև հաջորդ `SUB`-ը կամ `EOF`-ը և շարունակում այնտեղից։

```cpp
std::vector<Subroutine::Ptr> subroutines;
while( !_lookahead.is(Token::Eof) ) {
    synchronize(subroutineSync,
        std::format("Սպասվում է 'SUB', բայց հանդիպել է {}։",
            _lookahead));

    if( _lookahead.is(Token::Subroutine) )
        subroutines.push_back(parseSubroutine());

    parseNewLines();
}
```

Հաջողությամբ կառուցված բոլոր ենթածրագրերը վերջում միավորվում են մեկ
`Program` հանգույցում։ Նույնիսկ սխալի դեպքում հնարավորության սահմաններում
ստանում ենք մասնակի ծրագիր. ախտորոշումների առկայությունն է որոշում, որ այն
չպետք է փոխանցել կոմպիլյատորի հաջորդ փուլին։


### Ենթածրագրի վերնագիրը

Կեռասի ենթածրագրի ընդհանուր ձևն է.

```text
SUB name [(parameters)] [AS returnType]
    statements
END SUB
```

`parseSubroutine()`-ը նախ պահում է `SUB` տարրի տողը, ապա կարդում է
ենթածրագրի անունը։ Եթե հաջորդ տարրը `(` է, վերլուծվում է ստորակետերով
բաժանված պարամետրերի ցուցակը։ `()` դատարկ ցուցակը նույնպես թույլատրելի է։
Փակագծերից հետո ընտրովի `AS`-ը նշանակում է, որ ենթածրագիրը արժեք վերադարձնող
ֆունկցիա է։ `AS`-ի բացակայության դեպքում այն պրոցեդուրա է։

Ապա `parseSequence()`-ով կառուցվում է մարմինը և `parseBlockEnd()`-ով
պահանջվում `END SUB` զույգը։ Ստացված տվյալներից կառուցվում է
`Subroutine` հանգույց։

Պարամետրն ունի անուն, ընտրովի դատարկ `[]` նշում և պարտադիր տիպ։ Օրինակ.

```basic
SUB Find(needle AS TEXT, values[] AS TEXT) AS BOOL
    ' ...
END SUB
```

Այստեղ `needle`-ը պարզ `TEXT` պարամետր է, `values`-ը՝ `TEXT` տարրերի զանգված,
իսկ ենթածրագրի վերադարձվող տիպը `BOOL` է։ Պարզ ու զանգվածային պարամետրերը
ծառում ներկայացվում են նույն `Dim` հանգույցով։ Զանգվածային պարամետրի
`ArrayType` օբյեկտը չափ չունի, որովհետև զանգվածի իրական չափը փոխանցվում է
կանչի ժամանակ։

Տիպը վերլուծող `parseType()`-ը նախ պահանջում է `AS` բառը, ապա ընդունում է
միայն `REAL`, `TEXT` կամ `BOOL`։ Եթե տիպը բացակայում կամ սխալ է,
`parseParameter()`-ը դատարկ ցուցիչ է վերադարձնում, և այդ պարամետրը չի
ավելացվում ծառին։ Այսպես մասնակի AST-ում չի հայտնվում հորինված տիպով հանգույց։


## Նոր տողերն ու հրամանների հաջորդականությունը

Կեռասում նոր տողը շարահյուսության մի մասն է։ Ենթածրագրի վերնագրից և ամեն մի
հրամանից հետո պետք է լինի առնվազն մեկ նոր տող։ `parseNewLines()` մեթոդը հենց
այդ կանոնն է իրականացնում.

```cpp
void Parser::parseNewLines()
{
    if( !_lookahead.is(Token::NewLine, Token::Eof) )
        _diagnostics.mark(_lookahead.line,
            std::format("Սպասվում է տողի ավարտ, բայց հանդիպել է {}։",
                _lookahead));

    while( _lookahead.is(Token::NewLine) )
        advance();
}
```

Մեթոդը մեկ նոր տող է պահանջում, բայց հանդիպած բոլոր հաջորդական նոր տողերը բաց
է թողնում։ Հետևաբար երկու հրաման նույն տողի վրա գրել չի կարելի, իսկ դրանց միջև
դատարկ տողերի քանակը նշանակություն չունի։

Ենթածրագրի ու ամեն մի բլոկի մարմինը ծառում ներկայացվում է `Sequence`
հանգույցով։ `parseSequence()`-ը նախ ավարտում է նախորդ տողը, ապա հրամաններ է
հավաքում մինչև `END`, `ELSEIF`, `ELSE`, հաջորդ `SUB` կամ `EOF` տարրը։
`ELSEIF`-ն ու `ELSE`-ը չեն սպառվում. դրանք պետք են արտաքին `parseIf()`
մեթոդին։ Այս եղանակով ներդրված բլոկները մշակվում են առանց առանձին խորության
հաշվիչ պահելու։

`parseStatement()`-ն ըստ առաջին պիտակի ընտրում է հրամանը վերլուծող մեթոդը.

```cpp
if( _lookahead.is(Token::Let) )
    return parseLet();
if( _lookahead.is(Token::Dim) )
    return parseDim();
if( _lookahead.is(Token::If) )
    return parseIf();
// ... WHILE, FOR, CALL և RETURN
```

Ամեն մի վերլուծող մեթոդ վերադարձնում է `Statement::Ptr`, իսկ
`parseSequence()`-ը դրանք նույն հերթականությամբ հավաքում է `Sequence::_items`
ցուցակում։


## Հայտարարումներն ու վերագրումները

`DIM` հրամանը սահմանվում է այս կանոնով.

```ebnf
Dim = 'DIM' IDENT [ '[' Expression ']' ] 'AS' TypeName.
```

`parseDim()`-ը `DIM` բառից հետո կանչում է `parseDeclaration()` մեթոդը։
Վերջինս կարդում է անունը, ընտրովի զանգվածային չափն ու պարտադիր տիպը։

```basic
DIM count AS REAL
DIM names[10] AS TEXT
DIM flags[count + 1] AS BOOL
```

Եթե `[` փակագիծը հանդիպել է, տեղային զանգվածի համար դրա ներսում չափի
արտահայտությունը պարտադիր է։ Պարամետրի `values[] AS TEXT` ձևից սա տարբերվում
է. պարամետրի զանգվածը բաց է, իսկ տեղային զանգվածը պետք է չափ ունենա։

Parser-ն այստեղ միայն կառուցվածքն է ճանաչում։ Այն չի ստուգում, որ `count`
անունը հայտարարված է կամ չափի արտահայտությունն ունի դրական ամբողջ `REAL`
արժեք։ Այդ հարցերը պատկանում են հաջորդ՝ իմաստային վերլուծությանը։

Վերագրման `LET` հրամանի կանոնն է.

```ebnf
Let = 'LET' IDENT [ '[' Expression ']' ] '=' Expression.
```

`parseLet()`-ը պահում է հրամանի տողը, կարդում նպատակային անունը, ընտրովի
ինդեքսը, `=` նշանը և աջ կողմի արտահայտությունը։

```basic
LET total = total + value
LET values[index + 1] = 0
```

Ձախ կողմի անունից ստեղծվում է `Variable` հանգույց։ Ինդեքսը, եթե կա, պահվում
է անմիջապես `Let` հանգույցի առանձին դաշտում, իսկ աջ կողմը՝ որպես ընդհանուր
`Expression`։ Parser-ը չի որոշում՝ անունը պարզ փոփոխական է, զանգված է, թե
ընդհանրապես հայտարարված չէ։ Այն նաև չի համեմատում վերագրվող ու նպատակային
արժեքների տիպերը։


## Ղեկավարող կառուցվածքները

Կեռասն ունի ճյուղավորման `IF` և կրկնությունների `WHILE` ու `FOR`
կառուցվածքները։ Դրանց բոլորի մարմինները վերլուծվում են նույն
`parseSequence()` մեթոդով, իսկ ավարտը՝ `parseBlockEnd()`-ով։


### Ճյուղավորումը

`IF` հրամանը կարող է ունենալ մի քանի պայմանով ճյուղ և մեկ ընտրովի այլընտրանք.

```ebnf
If = 'IF' Expression 'THEN' Sequence
     { 'ELSEIF' Expression 'THEN' Sequence }
     [ 'ELSE' Sequence ]
     'END' 'IF'.
```

Առաջին `IF`-ն ու ամեն մի `ELSEIF`-ը վերլուծվում են ընդհանուր
`parseIfBranch()` մեթոդով։ Այն կարդում է բանալի բառը, պայմանը, պարտադիր
`THEN`-ը և ճյուղի մարմինը։ Կառուցված `IfBranch` հանգույցները հավաքվում են
վեկտորում։

Եթե հաջորդը `ELSE` է, դրա համար պայման չի կառուցվում. միայն վերլուծվում է
այլընտրանքային `Sequence` մարմինը։ Վերջում `parseBlockEnd(Token::If)` կանչը
պահանջում է `END IF`։ Parser-ը դեռ չի ստուգում, որ պայմանների տիպը `BOOL` է։


### Նախապայմանով ցիկլը

`WHILE` հրամանի կառուցվածքն ավելի պարզ է.

```ebnf
While = 'WHILE' Expression Sequence 'END' 'WHILE'.
```

`parseWhile()`-ը պահում է `WHILE`-ի տողը, վերլուծում պայմանն ու մարմինը և
պահանջում `END WHILE` վերջավորությունը։ Պայմանի ու մարմնի միջև առանձին
`THEN` կամ `DO` բառ չկա. դրանց սահմանը նոր տողն է։


### Հաշվիչով ցիկլը

`FOR` հրամանը հինգ հիմնական մաս ունի՝ հաշվիչը, սկզբնական արժեքը, վերջնական
արժեքը, քայլն ու մարմինը.

```ebnf
For = 'FOR' IDENT '=' Expression 'TO' Expression
      [ 'STEP' [ '+' | '-' ] NUMBER ]
      Sequence 'END' 'FOR'.
```

`parseFor()`-ը հաշվիչի անունից `Variable` հանգույց է կառուցում, ապա վերլուծում
`=`-ից հետո սկզբնական ու `TO`-ից հետո վերջնական արտահայտությունները։ Եթե
`STEP` մասը բացակայում է, parser-ն ինքն է ստեղծում `1.0` արժեքով `Number`
հանգույց։

`STEP`-ից հետո քերականությունը թույլ է տալիս միայն ընտրովի նշանով թվային
լիտերալ, ոչ թե կամայական արտահայտություն։ Օրինակ, `STEP -2` ձևը վերլուծելիս
մինուսի պիտակը կարդացվում է առանձին, իսկ `2`-ից կառուցված հանգույցը
փոխարինվում է `-2.0` արժեքով `Number` հանգույցով։

Իմաստային վերլուծիչն է հետագայում ստուգում, որ հաշվիչն ու սահմանները `REAL`
լինեն, իսկ քայլը զրո չլինի։


### Բլոկի ավարտը

`SUB`, `IF`, `WHILE` և `FOR` կառուցվածքները բոլորն ավարտվում են `END` բառով ու
իրենց տեսակը կրկնող երկրորդ բառով։ Այդ ընդհանուր գործողությունը կատարում է
`parseBlockEnd()` մեթոդը.

```cpp
void Parser::parseBlockEnd(Token keyword)
{
    if( !_lookahead.is(Token::End) ) {
        _diagnostics.mark(_lookahead.line,
            std::format("Սպասվում է 'END {}', բայց հանդիպել է {}։",
                keyword, _lookahead));
        return;
    }

    advance();
    match(keyword);
}
```

Այս ստուգման շնորհիվ, օրինակ, `WHILE` բլոկը `END IF`-ով փակելը չի ընդունվում։
Եթե `END`-ն ընդհանրապես բացակայում է, մեթոդը սխալ է գրանցում՝ առանց արտաքին
կառուցվածքի հնարավոր սկզբնական տարրը սպառելու։


## Պրոցեդուրայի կանչն ու արժեքի վերադարձը

Ենթածրագրի կանչը Կեռասում երկու շարահյուսական ձև ունի։ Պրոցեդուրան կանչվում է
`CALL` հրամանով՝ առանց փակագծերի.

```basic
CALL Print "Hello!"
CALL Move x, y
CALL Reset
```

`parseCall()`-ը կարդում է `CALL`-ը, ենթածրագրի անունը և
`parseExpressionList()`-ով՝ արգումենտները։ Եթե անունից հետո արտահայտություն
չի սկսվում, ցուցակը դատարկ է։ Հակառակ դեպքում արտահայտությունները բաժանվում
են ստորակետերով։

Ֆունկցիայի կիրառումը հրաման չէ, այլ արտահայտություն և գրվում է
փակագծերով.

```basic
LET line = Input()
LET maximum = Max(left, right)
```

Երբ `parseIdentifier()`-ը անունից հետո `(` չի տեսնում, կառուցում է սովորական
`Variable` հանգույց։ Եթե `(` կա, վերլուծում է ընտրովի արգումենտների ցուցակը,
պահանջում փակող `)`-ն և կառուցում `Apply` հանգույց։

Parser-ը միտումնավոր չի որոշում՝ `CALL`-ով իրո՞ք պրոցեդուրա է կանչվում, իսկ
փակագծերով՝ արժեք վերադարձնող ֆունկցիա։ Այն չգիտի նաև պարամետրերի սպասվող
քանակներն ու տիպերը։ Այս ամենը կանչվող անունի հայտարարությունից կախված
իմաստային հարցեր են։

Ֆունկցիայից արժեք է վերադարձնում `RETURN` հրամանը.

```ebnf
Return = 'RETURN' Expression.
```

`parseReturn()`-ը բանալի բառից հետո պարտադիր արտահայտություն է վերլուծում և
կառուցում `Return` հանգույց։ Արդյոք այս հրամանը ֆունկցիայի մարմնո՞ւմ է, արդյոք
արժեքի տիպը ճի՞շտ է և ֆունկցիայի բոլոր ուղիները վերադարձնո՞ւմ են արժեք՝ նորից
ստուգվում է իմաստային փուլում։


## Արտահայտությունների վերլուծությունը

Արտահայտությունները parser-ի ամենահետաքրքիր մասն են։ Այստեղ պետք է ոչ միայն
ճանաչել լիտերալներն ու գործողությունները, այլ նաև ճիշտ արտացոլել դրանց
նախապատվությունն ու զուգորդականությունը։ `1 + 2 * 3` գրառման համար գումարումն
ու բազմապատկումը նույն հերթականությամբ հանգույցներ դարձնելը սխալ ծառ կտար.
բազմապատկումը պետք է գտնվի գումարման աջ ենթածառում։

Կեռասի արտահայտության քերականությունը բաժանված է նախապատվության մակարդակների։
Ցածրից բարձր դրանք հետևյալն են.

| Մակարդակ | Գործողություններ | Զուգորդականություն |
|:---------|:-----------------|:-------------------|
| դիզյունկցիա | `OR` | ձախ |
| կոնյունկցիա | `AND` | ձախ |
| ժխտում | `NOT` | աջ |
| հավասարություն | `=`, `<>` | չի զուգորդվում |
| համեմատություն | `>`, `>=`, `<`, `<=` | չի զուգորդվում |
| գումարում | `+`, `-`, `&` | ձախ |
| բազմապատկում | `*`, `/`, `\`, `MOD` | ձախ |
| աստիճան | `^` | աջ |
| ունար նշան | `+`, `-` | աջ |
| ինդեքս | `[...]` | չի կրկնվում |
| պարզ արտահայտություն | լիտերալ, անուն, կանչ, փակագծեր | — |

Ամեն մի մակարդակի մեթոդ նախ կանչում է իրենից բարձր նախապատվություն ունեցող
մակարդակը։ `parseExpression()`-ը սկսում է ամենացածրից՝
`parseDisjunction()`-ից, իսկ կանչերի շղթան վերջում հասնում է
`parseFactor()`-ին։

Դիտարկենք այս արտահայտությունը.

```basic
1 + 2 * 3 OR FALSE
```

Բազմապատկումն ավելի բարձր մակարդակ է, ուստի `2 * 3` ենթածառը պատրաստվում է
մինչև գումարման հանգույցը։ Վերջում `OR`-ը դառնում է ամբողջ ծառի գագաթը.

```text
        OR
       /  \
      +   FALSE
     / \
    1   *
       / \
      2   3
```


### Ձախ-զուգորդական գործողությունները

`OR`, `AND`, գումարման և բազմապատկման մակարդակները ձախ-զուգորդական են։ Դրանց
մեթոդները նույն կաղապարով են կառուցված։ Օրինակ, գումարումը.

```cpp
Expression::Ptr Parser::parseAddition()
{
    auto result = parseMultiplication();
    while( _lookahead.is(Token::Add, Token::Sub, Token::Amp) ) {
        const auto token = _lookahead.kind;
        const auto line = _lookahead.line;
        match(token);
        result = node<Binary>(
            operation(token),
            std::move(result),
            parseMultiplication(),
            line);
    }
    return result;
}
```

Սկզբում կառուցվում է առաջին՝ ավելի բարձր մակարդակի ենթաարտահայտությունը։
Ամեն հաջորդ գործողության համար նախկին `result`-ը դառնում է նոր `Binary`
հանգույցի ձախ զավակը։ Ուրեմն `a - b - c` գրառումը կառուցվում է որպես
`(a - b) - c`։


### Չզուգորդվող համեմատությունները

Հավասարության ու համեմատության մակարդակներում `while`-ի փոխարեն `if` է։
Հետևաբար նույն մակարդակի գործողությունը կարող է հանդիպել առավելագույնը մեկ
անգամ։ Օրինակ, `a < b < c` շղթան Կեռասի մեկ արտահայտություն չէ։

Սակայն հավասարությունն ու կարգային համեմատությունն առանձին մակարդակներ են։
Այդ պատճառով `a < b = c > d` գրառումը քերականորեն հնարավոր է և համեմատում է
երկու համեմատությունների արդյունքները։ Արդյոք ստացված տիպերն իմաստային առումով
թույլատրելի են՝ որոշվում է հաջորդ փուլում։


### Աջ-զուգորդական գործողությունները

Աստիճան բարձրացնելու `^` գործողությունն աջ-զուգորդական է։ Դա ստացվում է,
որովհետև `parsePower()`-ն իր աջ մասի համար նորից կանչում է հենց իրեն.

```cpp
Expression::Ptr Parser::parsePower()
{
    auto result = parseUnary();
    if( _lookahead.is(Token::Pow) ) {
        const auto line = _lookahead.line;
        match(Token::Pow);
        result = node<Binary>(
            Operation::Pow,
            std::move(result),
            parsePower(),
            line);
    }
    return result;
}
```

Այսպիսով `a ^ b ^ c` արտահայտությունը դառնում է `a ^ (b ^ c)`։

`NOT` ժխտումն էլ է աջ-զուգորդական։ `parseNegation()`-ը, հանդիպելով `NOT`,
օպերանդի համար ռեկուրսիվ նորից իրեն է կանչում։ Արդյունքում `NOT NOT flag`
գրառումը կառուցվում է որպես `NOT (NOT flag)`։


### Ունար պլյուսն ու մինուսը

Մի քանի հաջորդական `+` և `-` նշանները `parseUnary()` մեթոդը նախ հավաքում է
վեկտորում։ Այնուհետև վերլուծում է ինդեքսավորման մակարդակը և գործողությունները
հակառակ հերթականությամբ ավելացնում ծառին.

```cpp
auto result = parseSubscript();
for( auto iterator = operators.rbegin();
     iterator != operators.rend();
     ++iterator )
    result = node<Unary>(*iterator, std::move(result), line);
```

Այդ պատճառով `-+value` գրառման ծառը `-(+value)` է։

Նախապատվությունների աղյուսակից երևում է նաև մի գուցե անսովոր, բայց
քերականությամբ հստակ որոշված հատկություն։ Ունար նշանն աստիճանից բարձր
նախապատվություն ունի, հետևաբար `-2^2` արտահայտությունը Կեռասում նշանակում է
`(-2)^2`, ոչ թե `-(2^2)`։


### Ինդեքսավորումը

Ինդեքսավորման `a[i]` գրառումը ծառում ներկայացվում է սովորական `Binary`
հանգույցով։ Նրա գործողությունը `Operation::Index` է, ձախ զավակը՝
ինդեքսավորվող արտահայտությունը, իսկ աջը՝ ինդեքսը։

`parseSubscript()`-ը թույլ է տալիս մեկ `[...]` մաս։ Այսպիսով Կեռասի ընթացիկ
քերականությունն ուղղակիորեն չի ճանաչում `matrix[i][j]` շղթան։ Սա
համապատասխանում է լեզվի միաչափ զանգվածներին։

Նկատենք, որ `LET a[i] = value` հրամանի ձախ կողմի ինդեքսը `Binary` հանգույց չի
դառնում։ Այն պահվում է անմիջապես `Let` հանգույցում, որովհետև վերագրման ձախ
կողմը պետք է սկսվի կոնկրետ փոփոխականի անունով։


### Պարզ արտահայտությունները

Նախապատվությունների շղթայի ամենավերջում `parseFactor()` մեթոդն է։ Այն ճանաչում
է.

* `TRUE` և `FALSE` տրամաբանական լիտերալները,
* թվային ու տեքստային լիտերալները,
* փոփոխականի անունը կամ ֆունկցիայի կիրառումը,
* `(` և `)` փակագծերի մեջ վերցրած արտահայտությունը։

Տրամաբանական լիտերալից կառուցվում է `Boolean`, թվայինից՝ `Number`,
տեքստայինից՝ `Text` հանգույց։ Scanner-ն արդեն հեռացրել է տեքստի չակերտները,
ուստի `Text`-ին փոխանցվում է միայն ներսի արժեքը։

Թվային բառույթի տեքստը `parseNumber()` մեթոդը `std::stod()`-ով փոխակերպում է
`double` արժեքի։ Scanner-ն արդեն ստուգել է թվի կառուցվածքը, բայց փոխակերպման
հնարավոր բացառությունը միևնույն է մշակվում է։ Այդ դեպքում գրանցվում է
ախտորոշում և ստեղծվում `0.0` պահուստային հանգույց, որպեսզի ծառի կառուցումը
հնարավոր լինի շարունակել։

Խմբավորման փակագծերն առանձին AST հանգույց չեն ստեղծում։ Օրինակ,
`(1 + 2) * 3` արտահայտության մեջ parser-ը վերադարձնում է հենց ներսի գումարման
հանգույցը, որը հետո դառնում է բազմապատկման ձախ զավակը։ Փակագծերի դերը միայն
վերլուծության հերթականությունը փոխելն է։


## Սխալներից վերականգնումը

Իրական ծրագրում հաճախ մեկից ավելի շարահյուսական սխալ է լինում։ Եթե parser-ը
առաջինի վրա կանգնի, ծրագրավորողը ստիպված կլինի սխալները մեկ առ մեկ ուղղել ու
ամեն անգամ նորից գործարկել կոմպիլյատորը։ Ավելի հարմար է մեկ անցումով գտնել
իրարից անկախ հնարավորին չափ շատ սխալներ։

Կեռասի parser-ը կիրառում է _խուճապի վիճակից վերականգնման_՝ panic-mode
recovery-ի եղանակը։ Սխալ հանդիպելիս այն հաղորդագրություն է գրանցում, ապա
բառային տարրեր է բաց թողնում մինչև մի կետ, որտեղից տվյալ կառուցվածքի
վերլուծությունը կարելի է վստահորեն շարունակել։

Ընդհանուր գործողությունը `synchronize()` մեթոդն է.

```cpp
void Parser::synchronize(
    const std::set<Token>& stops,
    std::string_view message)
{
    if( stops.contains(_lookahead.kind) )
        return;

    _diagnostics.mark(_lookahead.line, message);
    while( !stops.contains(_lookahead.kind) )
        advance();
}
```

`stops` բազմությունը պարունակում է անվտանգ կանգառները։ Եթե ընթացիկ տարրն
արդեն դրանցից մեկն է, ոչինչ անել պետք չէ։ Հակառակ դեպքում գրանցվում է մեկ
ախտորոշում և հոսքն առաջ է շարժվում մինչև կանգառը։

Վերականգնման երեք հիմնական բազմություններն են.

* `subroutineSync`՝ հաջորդ `SUB`-ը կամ `EOF`-ը գտնելու համար,
* `statementSync`՝ նոր տողը, հրամանների սկիզբներն ու բլոկների սահմանները
  գտնելու համար,
* `expressionSync`՝ արտահայտության հնարավոր սկիզբը կամ այն ավարտող `)`, `]`,
  ստորակետը, նոր տողը և բլոկային սահմանները գտնելու համար։

Օրինակ, եթե ենթածրագրի մարմնում անհայտ բառույթների շարք կա, parser-ը կարող է
դրանք բաց թողնել մինչև հաջորդ նոր տողը կամ ճանաչելի հրամանը և չկորցնել ամբողջ
մնացած ենթածրագիրը։ Վերին մակարդակի սխալ հատվածն էլ բաց է թողնվում մինչև
հաջորդ `SUB` հայտարարումը։


### Պահուստային հանգույցները

Դիտարկենք անավարտ վերագրումը.

```basic
LET result =
```

`parseExpression()` կանչերի շղթան վերջում հասնում է `parseFactor()`-ին, բայց
նոր տողի պիտակը պարզ արտահայտություն չէ։ Մեթոդը գրանցում է սխալ, որոնում
արտահայտության համաժամացման կետ և վերադարձնում `0.0` արժեքով `Number` հանգույց։

Այդ զրոն ծրագիրը ճիշտ չի դարձնում։ Այն միայն պահպանում է ծառի կառուցվածքը.
`Let` հանգույցը շարունակում է ունենալ աջ զավակ, և parser-ը կարող է անցնել
հաջորդ հրամանին։ Հետագա կոմպիլյացիան կանգնեցվում է `Diagnostics`-ում գրանցված
սխալի պատճառով։

Նույն նպատակի համար `match()`-ը բացակայող նույնացուցիչի փոխարեն դատարկ անուն է
վերադարձնում, `parseNumber()`-ը սխալ թվի դեպքում՝ զրո, իսկ տիպ չունեցող
պարամետրերն ու `DIM` հայտարարումները պարզապես չեն ավելացվում ծառին։ Ստացվում
է ոչ թե վավեր, այլ կառուցվածքային առումով հնարավորին չափ ամբողջական AST։


### Կրկնվող հաղորդագրությունների սահմանափակումը

Միևնույն բացակայող տարրը կարող է մի քանի իրար հաջորդող `match()` կանչերի
սխալ առաջացնել։ Որպեսզի ծրագրավորողը նույն պատճառի մասին մի քանի հաղորդագրություն
չստանա, `Diagnostics::mark()`-ը մեկ բառային տարրի վրա հաշվում է միայն առաջին
սխալը։

`mark()` կանչից հետո նոր հաղորդագրությունները ժամանակավորապես փակվում են։
Parser-ի հաջորդ հաջող `advance()` կանչը `Diagnostics::advance()`-ով նորից
բացում է դրանք։ Ուրեմն նոր բառային տարրին հասնելուց հետո կարելի է արդեն նոր
սխալ գրանցել։

`Diagnostics`-ը հաշվում է բոլոր հայտնաբերված սխալները, բայց հիշողության մեջ
պահում է առավելագույնը առաջին ութը՝ `MaxErrors` սահմանին համապատասխան։ Եթե
դրանք ավելի շատ են, հրամանային տողի ծրագիրը պահված հաղորդագրություններից հետո
ամփոփ ցույց է տալիս նաև բաց թողնվածների քանակը։


## Տողերը և AST հանգույցները

Scanner-ի ամեն մի բառային տարր պահում է ծրագրի տողի համարը։ Parser-ը այդ
տեղեկությունը փոխանցում է կառուցվող հանգույցներին։ Ենթածրագրի տողը `SUB`
բառինն է, հրամանինը՝ նրա բանալի բառինը, իսկ երկտեղանի գործողության տողը՝
գործողության նշանինը։ Լիտերալներն ու փոփոխականները պահում են իրենց բառույթի
տողը։

Սա միայն շտկման համար նախատեսված օժանդակ տեղեկություն չէ։ Հաջորդ՝ իմաստային
վերլուծության փուլում անծանոթ անունը, սխալ տիպի օպերանդը կամ անվավեր
վերագրումը պետք է կապել ծրագրի կոնկրետ տողի հետ։ AST հանգույցի `line` դաշտն է
տալիս այդ հնարավորությունը։

Հանգույցները կառուցվում են `node<T>()` օժանդակ կաղապարով և պահվում
`std::unique_ptr` ցուցիչներով։ Վերլուծության ավարտին վերադարձվող `Program`-ը
սեփականության տեսակետից ամբողջական ծառ է։ Այն այլևս կախված չէ scanner-ի
մուտքային հոսքից կամ parser-ի `_lookahead` դաշտից։


## Թեստերը

Բառային վերլուծիչի թեստերը գտնվում են `tests/scanner_test.cxx` ֆայլում։
Առանձին դեպքերով ստուգվում են թվային ու տեքստային լիտերալները,
նույնացուցիչները, ծառայողական բառերի տառաչափը, բոլոր գործողությունները, նոր
տողերը, մեկնաբանությունները, ֆայլի ավարտն ու սխալ նիշերի `Token::None`
արդյունքը։ `tests/lexeme_test.cxx`-ն էլ ստուգում է `Lexeme` դասը և բոլոր
պիտակների տեքստային ներկայացումները։

Բուն շարահյուսական վերլուծիչի թեստերը գրված են `tests/parser_test.cxx`
ֆայլում։ Դրանք ստուգում են ենթածրագրերն ու տիպավորված պարամետրերը,
`RETURN`-ը, գործողությունների նախապատվությունը, ինդեքսավորված վերագրումները,
ղեկավարող կառուցվածքները, սխալ մուտքի ախտորոշումը և բացակայող տիպով
հայտարարումների բաց թողնելը։

Թեստերից մեկը շրջում է `examples/` պանակի բոլոր `.bas` ֆայլերով և համոզվում,
որ դրանք համապատասխանում են Կեռասի քերականությանը։ Ընթացիկ նախագծում այդ
ստուգմանը մասնակցում է 19 օրինակ։

Ամբողջ նախագիծը կարելի է կառուցել ու փորձարկել հետևյալ հրամաններով.

```bash
$ cmake -S . -B build
$ cmake --build build
$ ctest --test-dir build --output-on-failure
```

Այս փուլից հետո նիշերի հոսքը նախ վերածված է պիտակավորված բառային տարրերի, ապա՝
ենթածրագրերի, հրամանների ու արտահայտությունների ծառի։ Շարահյուսական սխալները
կուտակված են իրենց տողերի համարներով, իսկ հաջող վերլուծության դեպքում
`Program` հանգույցը պատրաստ է հաջորդ՝ իմաստային վերլուծության փուլին։
