# Կեռասի runtime-ի պահանջները

## 1. Նպատակ և սահմաններ

Runtime-ը՝ կատարման ժամանակի գրադարանը, Կեռասի ծրագրի կողմից օգտագործվող 
փոքր օժանդակ գրադարան է։ Դրանում ներառված են այն գործողությունները, որոնք 
նպատակահարմար չէ կամ անհնար է ամբողջությամբ արտածել գեներացված կոդի մեջ.

* դինամիկ տեքստային արժեքների ստեղծում, պատճենում, միակցում և ոչնչացում,
* դինամիկ, միաչափ զանգվածների ստեղծում, ոչնչացում և տարրերին դիմում,
* ստանդարտ ներմուծում/արտածում,
* կատարման ժամանակի սխալների ստուգում և ազդարարում։

Runtime-ը լեզվի իմաստաբանությունը փոխարինող շերտ չէ։ Տիպերի ստուգումը,
անունների տեսանելիությունը, `RETURN`-ի պարտադիր լինելը և անհնարին ծրագրերի
մերժումը կատարվում են իմաստային վերլուծիչում։ Runtime-ը, այնուամենայնիվ,
պետք է ստուգի այն պայմանները, որոնք միայն կատարման պահին կարող են հայտնի
լինել՝ օրինակ զանգվածի չափը կամ ինդեքսի սահմանը։

Այս փաստաթուղթը նկարագրում է runtime-ի արտաքին ինտերֆեյսի կոնտրակտը և 
հիշողության կառավարման կանոնները։ Կեռասի կոմպիլյատորն ունի երկու backend՝ 
C կոդի գեներատոր և LLVM IR գեներատոր։ Երկուսն էլ պետք է օգտագործեն նույն 
runtime գրադարանը և նույն ABI-ն։

## 2. Երկու backend-ների ընդհանուր ABI-ն և հիմքային արժեքներ

Runtime-ի արտաքին ֆունկցիաները պետք է ունենան C ABI, որպեսզի դրանք
հնարավոր լինի կանչել թե՛ C backend-ի գեներացրած C կոդից, թե՛ LLVM IR 
backend-ի գեներացրած IR-ից։ Արտաքին հայտարարությունները պետք է գտնվեն
`runtime/include/*.h` ֆայլերում։

Երկու backend-ները պարտավոր են նույն կերպ.

* ներկայացնել տեքստերն ու զանգվածները,
* փոխանցել ծրագրի տեքստի տողի համարը կատարման ժամանակի սխալների համար,
* կանչել նույն create/copy/move/destroy ֆունկցիաները,
* պահպանել ownership-ի և օբյեկտի կյանքի տևողության նույն կանոնները,
* օգտագործել նույն runtime սխալների և I/O-ի վարքը։

Backend-ը չպետք է runtime-ի գործողությունը վերաիրականացնի իր գեներացրած
կոդում կամ ստեղծի backend-ին հատուկ համարժեք ABI։ C կոդը և LLVM IR-ը կարող
են տարբեր լինել միայն կանչի ձևով և լոկալ արժեքների պահման եղանակով,
ոչ թե runtime-ի իմաստաբանությամբ։

Կեռասի պարզ տիպերի runtime ներկայացումները հետևյալն են.

| Կեռասի տիպ | Runtime ներկայացում     | Պայման |
|------------|-------------------------|--------|
| `BOOL`     | `bool`                  | Միայն `false` և `true` արժեքներ |
| `REAL`     | `double`                | IEEE 754-ի վարքը պահվում է, այդ թվում՝ ոչ վերջավոր արժեքների հնարավորությունը |
| `TEXT`     | `avium_text` կառուցվածք | Բայթերի հաջորդականություն և դրա երկարություն |

`REAL`-ը չի վերածվում ամբողջ տիպի նույնիսկ այն գործողություններում, որոնց
արդյունքը մաթեմատիկորեն ամբողջ է (`\`, `MOD`, զանգվածի չափ և ինդեքս)։
Այդ գործողությունների համար runtime-ը կատարում է անհրաժեշտ ստուգումը։

## 3. Տեքստերի ներկայացում

`TEXT` արժեքը ներկայացվում է հետևյալ ստրուկտուրայով.

```c
typedef struct avium_text {
    const char *data;
    size_t length;
    bool owned;
} avium_text;
```

Պահանջներ.

1. `data`-ն ցույց է տալիս `length` բայթանոց հաջորդականություն, որը
   ավարտվում է նաև զրոյական նիշով։ Տեքստային գործողությունները պետք է
   հիմնվեն `length`-ի վրա, ոչ թե միայն `strlen`-ի, որպեսզի հնարավոր լինի
   ճիշտ կառավարել դատարկ տողը և ապագայում ներքին զրո պարունակող տվյալները։
2. `owned == true` լինելու դեպքում `data`-ի հիշողությունը պատկանում է
   արժեքին և պետք է ազատվի `avium_text_destroy`-ով։ `owned == false`
   լինելու դեպքում runtime-ը այն չի ազատում։
3. Լիտերալները կարող են լինել չսեփականացված, իսկ runtime-ի կողմից
   ստեղծված արդյունքները (`Input`, `STR`, միացում և պատճենում) պետք է
   լինեն սեփականացված։
4. Կառուցվածքի սովորական պատճենումը թույլատրելի է միայն որպես ոչնչացվող
   ժամանակավոր դիտում։ Եթե արժեքը պահվում է կամ վերագրվում է մեկ այլ
   փոփոխականի, պետք է օգտագործվի պատճենում կամ տեղափոխում։
5. `avium_text_move_assign`-ը պետք է նախ ոչնչացնի թիրախի նախկին արժեքը,
   տեղափոխի աղբյուրի սեփականությունը և աղբյուրը դարձնի անվտանգ դատարկ
   չսեփականացված տեքստ։
6. Ցանկացած concat/copy/create գործողություն պետք է ստուգի երկարության
   գումարման գերլցումը և հիշողության հատկացման ձախողումը։

Տեքստերի համեմատությունը բայթային այբբենական համեմատություն է
(`memcmp`-ի իմաստով)։ Runtime-ը չի կատարում Unicode-ի նորմալացում,
տեղայնացված համեմատություն կամ կոդավորման փոխակերպում։ Կեռասի
տեքստի կոդավորումը պետք է պայմանավորվի որպես UTF-8 բայթերի հոսք, սակայն
այս շերտը նիշերի իմաստաբանական վերլուծություն չի կատարում։

Պարտադիր հիմնական գործողություններն են.

* ստեղծել և պատճենել տեքստ,
* ոչնչացնել տեքստ,
* տեղափոխումով վերագրել,
* միացնել երկու տեքստ,
* համեմատել երկու տեքստ,
* `REAL`-ը վերածել տեքստի (`STR`-ի runtime իրականացում),
* տեքստը խիստ ձևով վերածել `REAL`-ի (`NUM`-ի runtime իրականացում)։

`NUM`-ը անտեսում է սկզբի և վերջի բացատանիշերը, սակայն դրանց միջև պետք է
ընդունի ամբողջ թվային ներկայացումը։ Դատարկ, մասամբ կարդացված, գերլցում
ունեցող կամ անվավեր արժեքը սխալ է։ `REAL`-ի IEEE 754 ներկայացմանը
համապատասխան՝ `NUM`-ը ընդունում է նաև `inf`, `infinity` և `nan` արժեքները՝
առանց տառաչափը տարբերելու։ `STR`-ը պետք է օգտագործի նույն `%.17g` ձևաչափը,
որը օգտագործվում է `Print`-ի համար, որպեսզի տեքստային ներկայացումները
հետևողական լինեն։

## 4. Զանգվածներ

Զանգվածը runtime-ում մի նկարագիրչ է, որը պահում է.

* տարրի տիպը (`BOOL`, `REAL` կամ `TEXT`),
* տարրերի դինամիկ բուֆերի հասցեն,
* տարրերի քանակը։

Զանգվածները միաչափ են, ունեն զրոյից սկսվող ինդեքսներ և փոխանցվում են
հղումով։ Ուստի ենթածրագրի մեջ կատարված տարրի վերագրումը տեսանելի է
կանչողին։ Descriptor-ի պատճենումը չպետք է կրկնապատկի բուֆերի
սեփականությունը. սեփականատերը պետք է լինի մեկ հստակ runtime օբյեկտ։

### Ստեղծում

`DIM a[n] AS T`-ի համար runtime-ը պետք է.

1. ստուգի, որ `n`-ը վերջավոր, դրական և ամբողջ `REAL` է,
2. ստուգի `n`-ի փոխարկելիությունը `size_t`-ի,
3. ստուգի նկարագրիչի և տարրերի բուֆերի չափերի գերլցումը,
4. հատկացնի զրոյացված բուֆեր,
5. վերադարձնի `T`-ի համապատասխան նկարագրիչ։

Զրոյացված բուֆերից `REAL`-ը ստանում է `0`, `BOOL`-ը՝ `false`։
`TEXT` տարրերը պետք է սկզբնավորվեն դատարկ, չսեփականացված տեքստով, որպեսզի
դրանց հետագա move-assign-ը անվտանգ լինի։ Չափը զրո չի թույլատրվում։

### Տարրին դիմելը և ոչնչացնելը

Տարրի հասցե վերադարձնող API-ն պետք է ստուգի.

* նկարագրիչի ոչ-զրոյական լինելը,
* սպասվող տարրի տիպի և նկարագրիչի տիպի համապատասխանությունը,
* ինդեքսի վերջավոր և ամբողջ լինելը,
* `0 <= index < length` պայմանը։

`TEXT`-երի զանգված ոչնչացնելիս նախ պետք է ոչնչացվեն բոլոր տարրերի
սեփականացված տեքստերը, ապա՝ տարրերի բուֆերը և նկարագրիչը։ `REAL` և
`BOOL` զանգվածների դեպքում տարրերի լրացուցիչ դեստրուկտոր պետք չէ։

Զանգվածի API-ն պետք է տարանջատի `TEXT`, `REAL` և `BOOL` տարրերի հասցեների
ֆունկցիաները, որպեսզի կոդի գեներատորը և C կոմպիլյատորը չստանան սխալ տիպով
տարր օգտագործելու հնարավորություն։

## 5. Ներկառուցված ենթածրագրեր և I/O

Իմաստային վերլուծիչում արդեն նախատեսված ներկառուցված ենթածրագրերը պետք է
ունենան runtime կապեր.

| Կեռասի անուն | Կեռասի ստորագրություն | Runtime վարք |
|---|---|---|
| `Print` | `Print(x)` | Արժեքը տպում է stdout-ում և ավարտում նոր տողով |
| `Input` | `Input() AS TEXT` | stdin-ից կարդում է մեկ տող՝ առանց վերջի newline-ի |
| `NUM` | `NUM(TEXT) AS REAL` | Խիստ թվային փոխարկում |
| `SQR` | `SQR(REAL) AS REAL` | Իրականացնում է քառակուսի արմատը |

`SQR`-ը բացասական վերջավոր արժեքի և բացասական անվերջության դեպքում
ավարտում է ծրագիրը runtime սխալով՝ նշելով կանչի source line-ը։ `NaN`-ի
արդյունքը մնում է `NaN`, դրական անվերջության արդյունքը՝ դրական
անվերջություն, իսկ բացասական զրոյի նշանը պահպանվում է։

`Print`-ի համար պետք է լինել `BOOL`, `REAL` և `TEXT` արժեքների առանձին
ABI ֆունկցիա։ `BOOL`-ը տպվում է `TRUE` կամ `FALSE`, `REAL`-ը՝
`%.17g` ձևաչափով, իսկ `TEXT`-ը՝ իր բայթերով։ Յուրաքանչյուր տարբերակ
ավելացնում է ճիշտ մեկ նոր տողի նիշ։

`Input`-ը պետք է աճող բուֆերով կարդա մինչև `\n` կամ EOF, հեռացնի
Windows-ի տողի ավարտի `\r`-ը և վերադարձնի սեփականացված `TEXT`։ EOF-ը
առանց կարդացված նիշերի պետք է համարվի դատարկ տող, եթե լեզվի հետագա
սպեցիֆիկացիան այլ վարք չի սահմանում։

Runtime-ը stdin/stdout-ը իրեն հատուկ կանոններով չի բուֆերացնում և
չի խառնում ախտորոշման հաղորդագրությունները stdout-ի հետ. սխալները
գրվում են stderr-ում։

## 6. Սխալների հաղորդում և խափանում

Runtime-ի յուրաքանչյուր գործողություն, որը կարող է սխալվել, պետք է
ստանա source line-ի համարը (`unsigned line`)։ Սխալի հաղորդագրությունը
պետք է ներառի այդ տողը և հայերեն բացատրություն, օրինակ՝
`<տող>: Զանգվածի ինդեքսը սահմաններից դուրս է։`

Առնվազն պետք է հաղորդվեն.

* հիշողության հատկացման ձախողումը,
* չափի կամ երկարության գերլրացումը,
* անվավեր զանգվածի չափը,
* դատարկ կամ սխալ նկարագրիչը,
* տիպի անհամապատասխան զանգվածային հասանելիությունը,
* ոչ ամբողջ կամ սահմաններից դուրս ինդեքսը,
* `NUM`-ի անվավեր մուտքը,
* stdin/stdout-ի I/O սխալը։

Սխալից հետո ծրագիրը պետք է ավարտվի non-zero կարգավիճակով և չվերադառնա
այնպիսի վիճակ, որը կթվա հաջող կատարում։ Մինչև runtime-ում առանձին
բացառություն կամ սխալի օբյեկտի ABI սահմանելը, գործող C իրականացումը 
կարող է օգտագործել stderr + `EXIT_FAILURE` քաղաքականությունը։ Հետագա
ընդլայնումը պետք է պահի նույն՝ «սխալը չկուլ տալ» պայմանը։

## 7. Կյանքի ցիկլ և երկու backend-ների պայմանագիրը

Յուրաքանչյուր backend պետք է հստակորեն կաևավարի դինամիկ օբյեկտի ստեղծում 
և ոչնչացում.

* լոկալ `TEXT` փոփոխականը դուրս գալիս ոչնչացվում է,
* լոկալ զանգվածը դուրս գալիս ոչնչացվում է,
* `TEXT`-երի զանգվածի յուրաքանչյուր տարրի վերագրումը նախ ոչնչացնում է 
  հին արժեքը,
* ֆունկցիայի վերադարձվող `TEXT` արժեքի սեփականությունը փոխանցվում է
  կանչողին,
* զանգված պարամետրը նկարագրիչի հղում է և չի ազատվում կանչվող
  ենթածրագրի ավարտին,
* պարզ պարամետրը փոխանցվում է արժեքով, ինչպես պահանջում է լեզվի
  իմաստաբանությունը։

Runtime API-ն պետք է կոմպիլացվի որպես ինքնուրույն C գրադարան, որը կարող 
է կապակցվել թե C backend-ի ստացած C ծրագրի հետ։ Մյուս կողմից LLVM IR 
backend-ի գեներացրած IR-ի հետ օգտագործելու համար runtime-ից պետք է ստեղծել
LLVM-ի `*.ll` ֆայլ։

## 8. Ընդունման չափանիշներ

Runtime-ի առաջին ամբողջական տարբերակը ընդունելի է, երբ.

1. բոլոր արտաքին ֆունկցիաները հասանելի են C ABI-ով և ունեն սահմանված
   ownership կոնտրակտ,
2. `BOOL`, `REAL`, `TEXT` արժեքները և երեք տեսակի զանգվածները կարող են
   ստեղծվել, օգտագործվել ու ոչնչացվել առանց leak/double-free-ի,
3. սխալ ինդեքսը, սխալ չափը, տիպի mismatch-ը, overflow-ը և անվավեր
   `NUM` մուտքը կանխատեսելիորեն ավարտում են ծրագիրը,
4. `Print`/`Input`-ի վարքը համապատասխանում է լեզվի սահմանմանը,
5. երկու backend-ների արդյունքները runtime-ի տեսանկյունից ունեն նույն
   observable behavior-ը՝ նույն մուտքի, ելքի և runtime սխալների դեպքում,
6. փորձնական ծրագրերը ծածկում են դատարկ տեքստը, տեքստային զանգվածի
   տարրի overwrite-ը, հղումով զանգվածի փոխանցումը, սահմանային ինդեքսները,
   `NUM`/`STR`-ը և I/O-ի սխալները։

## 9. Դիտարկման ենթակա հարցեր

Հաջորդ փուլում պետք է վերջնականապես որոշել հետևյալը.

* runtime-ի public ABI-ի versioning-ի ձևը,
* `TEXT`-ի UTF-8 պահանջը որպես պարտադիր լեզվական կանոն,
* uncaught runtime error-ի exit code-ը և հնարավոր stack trace-ը,
* արդյոք ապագայում պետք է ավելացնել runtime-ի garbage collector կամ
  պահպանել explicit ownership-ը,
* CMake-ում runtime-ը առանձին static library դարձնելու և C backend-ի
  ստացած C ծրագրի ու LLVM IR backend-ի ստացած object/executable ծրագրի հետ
  link անելու վերջնական կառուցվածքը,
* երկու backend-ների միջև runtime ABI-ի compatibility test-երի ձևաչափը։
